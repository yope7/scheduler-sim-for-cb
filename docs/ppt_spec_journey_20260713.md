- **目的**: 大学教授への進捗報告。研究の全体像（最終目標 → 現状 → 壁 → 今回の一手＝JAX による GPU 化 → 結果 → 残課題）を一本のストーリーで示す。**山場は「JAX の技術詳細」と「なぜ大規模で速くなったか＝計算量のオーダが変わった」**。

  1. 最終目標は「1 週間分（約 5 万ジョブ）のジョブで学習し、その週の最適 PF を描いて、管理者が週 1 回そこから運用点を選ぶ」こと。
  2. PF を描く（＝評価）段で **環境シミュレーション（配置探索）が律速**。これを **JAX で GPU に載せて大幅高速化**した。

## 3. 用語辞書（Glossary）★スライド S15 の中身 兼 表記統一の基準

**「正規表記」を全スライドで厳守**（言い換え・揺れ禁止）。

| 正規表記 | 略 | 教授向け定義 |
|---|---|---|
| **パレートフロント** | PF | クラウド費用と平均待ち時間の、両立をこれ以上良くできない境界の曲線。 |
| **ワークロード** | ― | ジョブ列の統計的な傾向（到着の密度・サイズ分布・実行時間の裾など）。「ワークロードタイプ」＝その傾向の種類。 |
| **週次運用** | ― | 1 週間分のジョブで学習し、その週の PF を描き、管理者が週 1 回そこから運用点を選ぶ運用像。 |
| **配置探索** | ― | 届いたジョブを「いつ・どのノードに置くか / クラウドに出すか」決める処理。評価計算の大半を占める。 |
| **エピソード** | ― | 全ジョブ列を頭から最後までシミュレーションし切る 1 回分。 |
| **ロールアウト** | ― | 方策に従いエピソードを実行して経験を集めること。 |
| **エピソード工場** | 工場 | GPU 上でエピソードを数百本まとめて量産する仕組み。今回の高速化の主役。 |
| **オンプレ** | ― | 自前クラスタ。空いていればどのノードに置いてもよい（非連続配置可）。 |
| **クラウド** | ― | 足りない分を借りる外部資源（クラウドバースティング）。 |
| **弾性クラウド** | ― | クラウドは実質いくらでも即時に借りられる＝順番待ちゼロ、とみなす近似。 |
| **イベント** | ― | 配置済みジョブの占有区間（開始時刻・終了時刻・占有ノード数の組）。配置探索はこの集合を掃いて空きを探す。 |
| **掃引配置** | sweep-line | 時間軸を左から右へ掃きながら「区間内で必要ノード数を満たせる最早時刻」を探す配置法。 |
| **N 軸消去** | ― | オンプレ空きを「どのノードが空きか（ノード 1 台ずつ）」でなく「何台空きか（数だけ）」で持つ最適化。ノード列（N 軸）が消える。 |
| **同時イベント枠** | E_alloc | GPU 実装で「同時に見るイベント数」を固定した上限（例 2,048）。これで 1 ステップの仕事量を一定にする。 |
| **JAX** | ― | NumPy とほぼ同じ書き方の数式を、そのまま GPU で高速実行できる数値計算ライブラリ（XLA・自動微分・vmap 付き）。 |
| **XLA** | ― | JAX の裏で数式を GPU 用の最適化済み機械語（カーネル）に変換するコンパイラ。 |
| **JIT（コンパイル）** | JIT | 関数を一度だけ GPU カーネルに変換し、以後は高速に走らせる仕組み。 |
| **vmap** | ― | 「1 本用に書いた処理」を書き換えず「N 本同時」へ自動拡張する変換（自動バッチ化）。 |
| **scan** | ― | 時間ステップの for ループを 1 つの GPU カーネルに融合し、毎ステップの CPU↔GPU 往復をなくす仕組み。 |
| **pmap** | ― | 複数 GPU にデータを分けて同じ処理を並列実行する変換（データ並列）。 |
| **カーネル** | ― | GPU 上で走る 1 つの計算処理のかたまり。 |
| **GPU 常駐** | ― | データが GPU メモリ上に置かれたままの状態（CPU 転送が起きない）。 |
| **CPU** | ― | 逐次・分岐の多い処理が得意な汎用プロセッサ。 |
| **GPU** | ― | 同じ計算の大量並列が桁違いに得意な演算装置。 |
| **Ray** | ― | CPU で複数プロセス（アクター）を並列に動かす分散実行ライブラリ。本研究では 16 アクター＝16 コア並列。 |
| **方策** | ― | 状態→行動を出すニューラルネット（AI 本体）。「ポリシー」不可。 |
| **指令** | ― | 方策に与える目標値（「この費用・この待ちを達成せよ」）。指令を変えて評価すると PF 上の別の点になる。 |
| **PCN** | PCN | Pareto Conditioned Networks。指令で条件付けして 1 方策に多数のトレードオフ点を学ばせる多目的強化学習。 |
| **バッチ** | B | 同時に並列処理するエピソード本数（B=256 なら 256 本同時）。 |
| **計算量オーダ** | O(・) | 入力サイズ（ジョブ数 N）に対し計算時間がどう伸びるかの型。O(N) は線形、O(N²) は二乗（超線形）。 |
| **秒/エピソード** | s/ep | 1 エピソードの実行にかかる実時間。 |

## ★ JAX 詳細（S8〜S13）── 教授の要望で実装の中身まで踏み込む

> このブロックは技術的に正確に。ただし各スライド冒頭に 1 行の「平たい要約」を必ず置く。図中・本文の数値は §7 と一致させる。

### S8. JAX とは（XLA と関数変換）
- 平たい要約: NumPy の数式を、そのまま GPU 用の最適化コードに変換して走らせる道具。
- 本文:
  - JAX = **NumPy 互換の数式** ＋ **XLA コンパイラ**（数式を GPU カーネルへ最適化変換）＋ **関数変換**。
  - 効いた関数変換 4 つ:
    - **`jit`**: 関数を一度だけ GPU 機械語にコンパイル、以後高速。
    - **`vmap`**: 1 本用の処理を自動で N 本同時（バッチ軸）に。
    - **`scan`**: 時間ループを 1 カーネルに融合、CPU↔GPU 往復を消す。
    - **`grad`**: 自動微分（学習側で使用）。
  - 教授向けの一言: **手で CUDA を書かずに、数式のまま GPU 並列コードが得られる**。
- ノート: この 4 つが後続スライドで具体的にどう効いたかを示す。

### S9. 何を GPU に載せたか（全体像）
- 平たい要約: エピソード 1 本まるごと（配置・報酬・観測・行動）を 1 つの GPU カーネルに融合し、B 本同時に流す。
- 本文（データフロー）:
  - 1 エピソード ＝ 「ジョブを 1 個ずつ ①配置探索 → ②報酬（待ち・費用）→ ③観測を更新 → ④方策 NN が次の行動」を最大 5 万ステップ繰り返す。
  - これを **`scan` で 1 カーネルに融合** ＋ **`vmap`/バッチ軸 B でエピソードを並列**（B=256〜1024）。
  - すべて **GPU 常駐**（CPU 転送を挟まない）。
- 図: 「ジョブ列 → [GPU: scan(配置→報酬→観測→方策)] × B 本 → 経験データ」。
- ノート: 従来は各ステップで CPU↔GPU を往復していた。それを無くしたのが効いた。

### S10. JAX 詳細①：配置探索の GPU 化とカーネル選択
- 平たい要約: 「空きを探す」計算を GPU 向けに 3 通り試し、一番相性の良い方式を選んだ。
- 本文（技術）:
  - 配置探索＝各時刻でイベント集合（占有区間）を掃き、「必要ノード数を満たせる最早時刻」を探す（掃引配置）。
  - GPU カーネルを 3 実装で比較:
    - **v1（fp16 の行列積 / einsum）**: 占有を密行列で表し `einsum` で一括評価。**XLA と相性が良く最速**。
    - **v2（差分 scatter＋cumsum）**: イベントの ± を散布して累積。**XLA の `scatter` が遅く不利**。
    - **v3（ソート）**: 大バッチで `scatter` 詰まり。
  - 結論: **v1（fp16 einsum）が全域で v2/v3 を上回る**（XLA の scatter が致命的に遅いため）。真の律速は「探索の帯域」で、int16 化＋gather のブロードキャストで改善。
  - 検証: **C 実装と約 5,700 問で全一致**（連続/非連続・密度・境界ケース）。
- 図: v1/v2/v3 の模式（密行列 vs 散布 vs ソート）。任意。
- ノート: 「GPU では素直な散布より、あえて密な行列積の方が速い」ことがある、という XLA の癖の実例。

### S11. JAX 詳細②：N 軸消去と弾性クラウド（オーダを削る 2 手）
- 平たい要約: オンプレは「空き台数」だけ数えれば置ける。クラウドは待ちゼロなので探索自体を省く。
- 本文（技術）:
  - **N 軸消去**: オンプレは非連続配置可＝「どの 5 台か」は待ち時間に無関係。だから占有を密行列 `(B,T,E,N)` で持つのをやめ、**高さ（占有ノード数）の和 `(B,T,E)` だけ**に。**ノード軸 N（例 1,520）を丸ごと消去** → einsum の最内次元が消える。配置に**実際に置く 1 回だけ**本当のノード番号を読む（全体の約 1/500）。結果は元と統計的に一致。
  - **弾性クラウド**: クラウドは順番待ちゼロ＝待ち 0。だから **クラウド側の空き探し（カーネル軸 2,048）を丸ごと省略**。物理的に正しい近似（費用への影響 約 −1%）。
- 図: 密行列 `(B,T,E,N)` → 高さ和 `(B,T,E)` の潰れ（§9 相当の絵、または既存 `gpu_speedup_20260708.html` の SVG を流用）。
- ノート: この 2 手が、次スライドの「オーダが変わった」に直結する。

### S12. JAX 詳細③：scan 融合・同時イベント枠・複数 GPU
- 平たい要約: 1 ステップの仕事量を固定枠にそろえ、二乗の重さを線形に落とし、GPU 2 枚で分担。
- 本文（技術）:
  - **`scan` 融合**: 最大 5 万ステップの for を 1 カーネルに。毎ステップの CPU↔GPU 往復（5 万往復）を消去。
  - **同時イベント枠 E_alloc（固定パディング）＋ scan 内圧縮（kcompact）**: 「同時に見るイベント数」を固定上限（例 2,048）に抑え、生存イベントを一定間隔で前詰め圧縮。これで **1 ステップの仕事量が一定** になり、素朴なら **O(N²)** の総計算量が **O(N·E_alloc)＝ほぼ O(N)** に。5 万ジョブでもメモリ数百 MB で完走。
  - **`vmap`/バッチ軸 B**: エピソードを 256〜1024 本並列。
  - **`pmap`（GPU 2 枚）**: データ並列でさらに約 2 倍。
- 図: 「O(N²) 曲線 → O(N) 直線」の概念（S14 と共有可）。
- ノート: E_alloc 固定が「オーダを変えた」中核。次スライドで数字とともに。

### S13. JAX 詳細④：正しさの担保（速いだけでは足りない）
- 平たい要約: GPU 版が CPU 版と同じ結果になることを、各段で突き合わせて確認した。
- 本文（技術）:
  - **方策の移植**: PyTorch の forward（`s_emb ⊙ c_emb` の Hadamard 積・sigmoid・log-softmax）を JAX へ移植。fp32 で **PyTorch と 3.2e-6 まで一致**。
  - **観測のタイ順問題 → ハイブリッド確定法**: 観測構築のソートで「同値のイベントの並び順」が実装依存になる。GPU の行列積 logits は CPU と完全ビット一致しない（偏差 約 2.4e-5）ため、**logits 差が 1e-3 未満の行だけ CPU 参照形状で再計算**（再計算率 0.03%）し、**行動列の完全一致を保証**。
  - **ビット一致検証**: 配置カーネル（C と約 5,700 問一致）・環境全ステップ・評価の行動列・工場データ分布（KS 検定 p>0.95）を各段で確認。
  - **JAX の落とし穴も明記**: ①GPU 常駐が前提（H2D/D2H 転送込みだと 1/3〜1/10 に低下）②ドライバの CUDA 12.2 と ptxas 12.9 の不一致で XLA の並列コンパイルが無効化 → 永続キャッシュで初回コンパイル（数十秒）を償却。
- ノート: 「結果を変えずに速くした」ことが、この研究で JAX を選んだ実利的な理由（純関数で検証しやすい）。

---

### S14. 結果 ── めっさ速い。ただし「オーダが変わった」から
- キーメッセージ: 大規模ほど大きく速い。理由は定数倍でなく計算量オーダの改善。
- 本文（実測・§7）:
  - 配置探索カーネル: 対 C（1 コア）**×11.8**（GPU 常駐時）。
  - 5 万ジョブ 1 エピソード: **CPU 1 コア 206.6 秒 → GPU 1 枚 2.81 秒（×73）**（対 16 コア ×4.6）。
  - **なぜこれほど？**: CPU は 1 ステップが O(生存イベント数) で総計算 **O(N²) 的（超線形）**。GPU 工場は E_alloc 固定で **O(N)（線形）**。→ **計算量のオーダが変わった**ので、**ジョブが多いほど差が開く**（128 ジョブでは僅差、5 万で大差）。
  - 図: **左＝`docs/figures/jax_speedup_20260712.png`**（実測）／**右＝O(N²) 曲線 vs O(N) 直線の概念**。
- ノート: 「×73 は速い実装というより、二乗を線形に落とした結果」——ここを強調。

### S15. 残課題と位置づけ
- キーメッセージ: 速度は解けた。だが「未知ワークロードへの精度（空間拡大）」はまだ手つかず。ただし高速に実験を回せるようになった。
- 本文:
  - 解けたこと: **大規模シミュレーションの速度**（5 万ジョブが現実時間で回る土台）。
  - 未着手: **空間拡大による精度**（未知ワークロード・5 万規模で「密な PF」を保証する精度）は **まだ手を打てていない**。
  - しかし: **実験を高速に回せるようになった**＝精度課題に多数の試行で挑める。次はこの土台で精度に取り組む。
  - （正直な注記）今回の速度は **大規模・大量評価でのみ効く**。普通サイズ（128〜512）の学習は律速が NN 側なので速くならない。
- ノート: 「速度＝目的でなく手段。次は精度（未知ワークロード）」で締める。

## 7. 確定データ（★この数値のみ使用可。測定 2026-07-12、GPU 搭載サーバ実機）

| 測定対象 | 比較基準 | 速度 | 前提・注記 |
|---|---|---|---|
| 配置探索カーネル（単体） | C 実装 1 コア | **×11.8** | GPU 常駐時。単発呼び（転送込み）だと **×1.5** |
| エピソード工場（128 ジョブ） | 16 コア CPU 並列 | **×3.6** | 対 1 コアなら ×57 |
| エピソード工場（512 ジョブ） | 16 コア CPU 並列 | **×2.5** | 対 1 コアなら ×40 |
| エピソード工場（50,000 ジョブ） | CPU 1 コア | **×73** | 対 16 コア並列なら ×4.6 |

- 5 万ジョブ 1 エピソードの生時間: **CPU 1 コア 206.6 秒 / GPU 1 枚 2.81 秒**。
- 評価（PF 描画）の計算内訳: **環境シミュレーション（配置探索）約 93%**。
- 学習ループ内のロールアウト内訳: **方策 NN 約 69% / 環境 約 30%**（＝学習では環境は脇役）。
- 従来の CPU 並列: **16 アクター（16 コア）**（Ray）。
- カーネル選択: **v1（fp16 einsum）が v2（scatter）/v3（sort）に勝つ**。C と約 5,700 問一致。
- 方策移植: PyTorch と **3.2e-6** 一致（fp32）。観測タイ順ハイブリッド確定法の再計算率 **0.03%**、行動列は完全一致。
- 環境: **JAX 0.4.28、CUDA GPU 2 枚（各 46 GB 級）**。warm 後・`block_until_ready` 同期で計測。
- （別測定・2026-07-08）GPU 内部の作り込みで 5 万ジョブ **9.0 秒 → 0.151 秒（60 倍）**。積み上げ: 9.0→4.78(カーネル訂正 ×1.9)→2.21(弾性クラウド ×2.2)→0.31(**N 軸消去 ×7.1**)→0.151(GPU 2 枚 ×1.9)。対 16 コア CPU 合成 22 倍・実トレース 5 倍。※ この 0.151 秒（2 GPU・全最適化）と今回の 2.81 秒（1 GPU・素直な設定）は **別条件の別測定**。混同・合成しない。
