## 1. CPU-GPU分業型RLとは

### 1スライド1メッセージ

CPU-GPU分業型RLでは、環境はCPU、ニューラルネットワークはGPUで動かす。

### 要点

- 環境シミュレーション: CPU / 方策推論・学習: GPU
- 一般的なRL実装に近く、Python/C++で複雑な環境を書きやすい
- 本プロジェクトの従来構成もこれ(Actor=環境+推論を全部CPU、Learner=学習だけGPU)

### メリット(本プロジェクトの実測つき)

- 実装しやすい・既存の環境コードをそのまま使える
- **環境1個あたりはCPUの方が速いことがある**: 実測で1決定あたり CPU 0.30ms vs GPUに1環境ずつ載せると0.48〜0.60ms(GPUの方が遅い)
- 少数rolloutなら効率がよい

### デメリット

- 毎ステップCPU-GPU間のやり取りが発生しやすい
- CPU側の環境実行が律速になりやすい
- GPUがNN計算待ちでなくCPU待ちで遊ぶ
- 大量rollout生成に向かない

---

## 2. GPUOnly型RLとは

### 1スライド1メッセージ

GPUOnly型RLでは、環境・観測・報酬・方策推論をできるだけGPU上で完結させる。

### 要点

- 環境シミュレーション・観測生成・報酬計算・方策推論もGPU
- 可能なら学習ループ全体もGPU上で回す

### 関連研究(原文確認済み6本)

- Isaac Gym (NVIDIA, NeurIPS 2021): 物理・報酬・観測を全部GPU常駐、従来比2〜3桁高速
- Brax (Google, 2021): JAXで物理エンジンごと書き直し
- **CuLE (NVIDIA, NeurIPS 2020): AtariエミュレータのCUDA移植。今回の「1スレッド=1エピソード」の直接の先行**
- Podracer/Anakin & Sebulba (DeepMind, 2021): GPU完結型と分業型の使い分けを明言
- Jumanji (InstaDeep, ICLR 2024): JobShop/BinPack等のJAX環境(ドメインが近い)
- Pgx (NeurIPS 2023): 囲碁・将棋・チェスのJAXシミュレータ

### メリット / デメリット

- ○ CPU-GPU間の往復を減らせる / 多数環境の並列rollout / CPU actor並列限界の回避 / ループ全体の融合
- × 環境のGPU向け書き直しが必要 / 分岐が多い処理は効率が落ちる / GPUメモリが新しい壁 / 正しさの検証が重い

## 3. 一般論の整理

### 1スライド1メッセージ

GPUOnly型は万能ではない。論文自身が「環境1個ならCPUが速い」「分岐と大きい状態が苦手」と認めている。

| 方式 | 向いている状況 | 苦手な状況 |
|---|---|---|
| CPU-GPU分業型 | 環境が複雑、既存コード活用、rollout少数 | 環境実行が重い、大量rollout、CPU同期が多い |
| GPUOnly型 | 大量環境の並列実行、転送・同期の削減 | 分岐が多い、状態が大きい、GPU実装が難しい |

### 要点(出典つき)

- CuLE自身が明記: 「環境1個あたりのFPSはCPUより遅い。**128環境以下ならCPUの方が効率的**」
- CuLE/Jumanji: 分岐(if文)はワープ内で遊ぶ人を作る(最大30%低下)/「全分岐を実行してから選ぶ」しかない
- Podracer(DeepMind): 環境をJAXで書けないなら分業型(Sebulba)を使え、と二本立てを明言

### 布石(次スライドへの繋ぎ)

> **そして本プロジェクトの環境(イベント駆動・分岐だらけ・生存イベント表数千行)は、この「苦手」側のど真ん中にある。**
> それでも成立させた工夫がスライド7。

## 4. PCNではどちらが適しているか

### 1スライド1メッセージ

5万ジョブでは環境rolloutのコストがジョブ数に対して超線形に増え、CPU側は64コア使い切っても天井。だからGPUOnly側に寄せる価値がある。

### 理由(定量)

- 1本のrollout=5万ステップの配置計算。しかも**ステップ単価もジョブ数で増える**: 実traceは生存イベントが刈り取れず、環境実行時間は実測 **n^1.75〜2.6 の超線形**(小規模では環境は脇役だが、大規模で主役に浮上する)
- PFを作るには多数の指令×多数のrolloutが必要(学習+評価)
- **CPU側の道は使い切った**: 64コア並列で11本/分が天井。マシン1台を独占してこの数字
- NNだけGPUに載せる分業型では、この環境コストがそのまま残る

### セリフ案

> PCNでは、ニューラルネットワークの学習よりも環境シミュレーションそのものが重くなります。ポイントはステップ数が多いことではなく、ジョブ数が増えるとステップ1回あたりの配置計算まで重くなる、つまり超線形に効いてくることです。実測ではジョブ数の1.75〜2.6乗で伸びます。CPU側は64コアを使い切っても毎分11本が天井で、ここから先はCPUの台数を増やす道しかありません。だから環境ごとGPUに寄せる価値があります。

## 5. Nsightで見えた律速

### 1スライド1メッセージ

PCIe転送(DMA)は無罪。重かったのは「細かいカーネル発行」と「毎ステップの待ち合わせ」、それと転送の"場所"ではなく"形"(オブジェクト⇄配列の変換)。

### 要点(2つの独立したNsight測定)

**測定①: NN推論1決定の解剖**(分業型Actorの推論をGPUに載せた場合)

| 項目 | 実測 |
|---|---:|
| データ転送 DMA(H2D+D2H) | **2.45μs = 全体の0.5%(無罪)** |
| GPUの実計算(カーネル33個) | 58μs |
| CPUからのカーネル発行(33回) | **133μs = 真のネック** |

**測定②: 既存GPU環境(XLA)の1ステップ約32msの内訳**(定常部275.6秒のSQL集計)

| 項目 | 実測 |
|---|---:|
| GPU計算(カーネル約340個/ステップ、平均11μs) | 〜3.9ms |
| GPU上のコピー(約340回/ステップ、各2MB) | 〜3.0ms |
| **発行・同期・すきま(CPUスレッドはcuStreamSynchronizeで83%ブロック)** | **〜25ms** |

- 1ステップ=伝票約680枚(カーネル340+コピー338)をCPUが発行。発行1枚約4.5μs×累計290万回
- 司会の動かぬ証拠: **4バイトのD2H読み戻し×25,764回**=ループを続けるかの判定値を毎回CPUが確認している

### 大事な訂正(過去の自分の報告への)

- 以前「転送がボトルネック」と報告したが、正確には**PCIeの転送量(DMA)は無罪**
- 本当に重かった「転送」は、Pythonオブジェクトを1個ずつ配列に詰め替える**変換**(実測75秒/8本で5万フル学習が一度死んだ)
- つまり**転送の「場所」ではなく「形」が壁**。GPUOnly化が効くのは「運ぶ量が減る」からではなく「オブジェクトを触る場所が消える」から

### セリフ案

> 一般論ではGPUOnly型の利点は転送削減と言われます。ただ、Nsightで測ると、PCIe上のデータ移動そのものは1決定あたり2.45マイクロ秒、全体の0.5%で無罪でした。重かったのは2つで、CPUが細かいカーネルを毎ステップ数百枚発行する時間と、各ステップでGPUの完了を待つ同期時間です。もう1つ、以前「転送が壁」と報告したことがありますが、あれの正体はPCIeではなく、Pythonオブジェクトを1個ずつ配列に詰め替える変換コストでした。転送の場所ではなく形が壁だった、というのが正確な言い方です。

## 6. 既存GPU実装の問題

### 1スライド1メッセージ

測定を剥がすたびに数字が下がる: ランプ100% → タイムライン94% → 正味の計算12% → スループットは手書き比1/37。「忙しそう」と「仕事が進む」は別物。

### 要点(Nsight、scan定常部275.6秒のSQL集計)

| 測定のレイヤ | 数字 |
|---|---|
| ① nvidia-smi(稼働ランプ) | sm=100% |
| ② タイムラインの占有 | 94%(うち**CUDA Graph実行の封筒72.8%**=中身の密度はこの記録粒度で不可視、個別カーネル12.0%、D2Dコピー9.4%) |
| ③ 個別に見える正味の計算 | **12.0%**(33.0秒) |
| ④ 最後の審判=スループット | **手書きカーネルの1/37**(同じGPU・同じ仕事) |

- D2Dコピーは290万回・平均2MB・**総量5.8TB**=状態の持ち回り(計算でなく引っ越し)
- CPUスレッドは**83%を`cuStreamSynchronize`でブロック**+毎周690枚の発行+4バイトの継続確認3回=司会構造

- dmonの「100%」は「サンプル期間中に1個でも仕事が載っていたか」の**稼働ランプ**であって出来高ではない
- 各ステップでCPUが「次のカーネルを発行→完了を待つ→次へ進むか判断」を繰り返す=制御ループがCPUに残っている
- この「伝票律速」は本プロジェクトで**3回目の再発**(推論のlaunch-bound、学習updateの発行律速、今回の環境実行)。GPU高速化の失敗第1位は「計算が遅い」ではなく「仕事を細かく渡しすぎ」

### セリフ案

> nvidia-smiはGPU使用率100%と言います。Nsightのタイムラインで見ると94%の時間「何か」はしています——ただしその73%はCUDA Graphの封筒で、個別に見える正味の計算は12%です。そして同じGPUで手書きカーネルは37倍進みます。「忙しそうに見える」と「仕事が進む」は、測るたびに乖離していく——これがプロファイラを当てて分かった一番大きなことです。原因はGPUの計算力ではなく、CPUが毎周司会をし、状態を2MB単位で引っ越し続ける構造の方でした。

## 7. 今回の方針: 手書きGPUカーネル

### 1スライド1メッセージ

CPUの司会をやめてrollout全体をGPU内で進める。「分岐だらけの環境はGPUが苦手」問題は、スレッド割当とアルゴリズム移植の2つの工夫で回避した。

### 方針

- 1ステップごとにCPUが制御しない。カーネル1回の起動でrolloutを最後まで進める
- **1スレッド=1エピソード**を担当(CuLE方式)し、多数本を横に並べる

### 工夫①: ワープ発散の構造的回避(tpb=1)

- 32スレッド束(ワープ)に別々のエピソードを入れると、分岐がバラバラで互いに待ち合う
- 実話: tpb=32で試したらワープ発散で32分/チャンクに劣化 → **1ブロック1スレッド(tpb=1)にして解消**

### 工夫②: CPUの賢いアルゴリズムをそのまま移植

- XLA/vmap流のベクトル化では、賢い逐次アルゴリズムが書けず「全件走査して捨てる」形に落ちる(Jumanjiも同じ告白をしている)
- 手書きカーネルなら、CPU版と同じ**sweep-line・増分更新・早期打ち切り**をそのまま持ち込める
- 実話: v1は毎候補で全イベント走査していて遅かった → 増分方式で**13倍**

### 速くなる理由(まとめ)

- CPU-GPUの待ち合わせと発行回数が激減(司会の排除)
- 無駄撃ちしない賢いアルゴリズム(GPUの流儀に負けて捨てない)
- rolloutを数百〜千本、横に並べられる

## 8. 実測結果①: rollout生成速度

### 1スライド1メッセージ

手書きGPUカーネルで、5万ジョブのrollout生成はCPU64コアの11倍・既存GPU実装の50倍。しかも近似なしでCPU版と全件一致。

| 方法 | 5万ジョブrollout生成速度 |
|---|---:|
| CPU 1コア | 0.25本/分 |
| 既存GPU実装(XLA) | 2.5本/分 |
| CPU 64コア | 11本/分 |
| **手書きGPUカーネル A40 1枚** | **93.5本/分** |
| **手書きGPUカーネル A40 2枚** | **125.4本/分** |

脚注(必ず入れる):
- 条件: weekB 5万ジョブ・cap48000/192000・バッファ溢れゼロ(厳密)。1枚=B1024本同時、2枚=512本×2
- **この表はPhase1(探索rollout、行動列は事前生成でNN推論を含まない)の生成速度**。NN込みは次スライド
- CPU64コアは48並列実測からの換算

### 口頭で強調する2点

- **既存GPU実装(2.5本/分)はCPU64コア(11本/分)に負けている**。GPUを使っても司会構造だと64コアCPU以下=前スライドの実働18%の帰結
- 2枚が1枚の2倍になっていないのは1枚あたりの本数を半分にした条件のため。むしろ**B=64→1024に増やしてもほぼ無料(374→657秒)=GPUの床はまだガラ空き**で、伸び代が残っている

### 正確性

- CPU版と**(開始時刻・待ち時間・費用)が50000/50000全件一致**
- 「速いが近似」ではなく、正しさを検証した上での高速化(7月に高速だが不正確なカーネルを一度作って捨てた教訓から、検証を先に設計)

## 9. 実測結果②: NN推論込みもGPU化済み(ロックステップ)

### 1スライド1メッセージ

先週「今後の課題」と言ったPhase3(環境+観測+NN推論のループ)も、この1週間でGPU内ロックステップ化が完成した。

### 要点

- 環境step+観測生成+NN推論(TorchScript)をGPU内で接続し、**ループ内のホスト同期ゼロ・1周わずか5発行**(伝票680枚→5枚)
- 発行コストは実測**1.15倍**まで圧縮(ほぼ消えた)
- 正確性は三段で厳密一致を確認:
  - 配置結果 30万項目一致
  - 観測 1,120万セル一致
  - **NN greedy行動 50,000/50,000ステップ×2本、実物チェックポイント+実指令で完全一致**
- 5万ジョブのPhase3が**定額11.4分/チャンク**(CPU版は序盤4分〜終盤96分のガチャ)+CPU64コアを他の仕事に解放

### セリフ案

> rollout生成だけでなく、ニューラルネットの推論を含むループも先週GPU内で完結させました。以前は1ステップに約680回あったCPUからの発行が5回になり、発行コストは1.15倍相当まで消えています。正しさは配置・観測・NNの行動の三段で、5万ステップ全件一致を確認済みです。

## 10. 正直スライド: 学習全体では何倍か

### 1スライド1メッセージ

rollout単体は50倍でも、学習全体は約1.3〜1.4倍(見込み)。全体のどこが残るかまで含めて設計している。

### 要点

- 学習にはrollout生成以外の部分(NN更新・リプレイ・評価)が残る=アムダールの法則
- **【8/24実測・v6フル装備完走】** 5万ジョブ・14イテレーション:
  - 学習本体(Phase1+2+iter1〜14+refit): **2時間52分**(03:31→06:23)
  - 学習中eval(16指令×5万rolloutのPF計測): **2時間38分**(06:23→09:01)
  - 全体 **5時間30分で正常完了**。refit精度 policy_acc **0.8521**(v3の0.798を上回る)
- 学習本体は見込み(3.5〜4時間)を下回った。全体はeval計測込みで5.5時間=**次の律速はeval計測とリプレイのオブジェクト経路**
- 「50倍」と「全体の倍率」を両方言うのが誠実: 50倍はrollout生成という部品の数字
- 注: 旧「約5時間」との厳密比較は工程構成(eval回数等)の突き合わせが必要なので、口頭では実測内訳をそのまま言うのが安全

### セリフ案

> 誤解のないように言うと、50倍というのはrollout生成という部品の数字です。フル装備版は今朝完走していて、学習本体は2時間52分、PFの計測を含めた全体では5時間半でした。学習にはネットワークの更新・リプレイ管理・評価計測が残っていて、そこはまだCPUとオブジェクト処理の世界にあります。逆に言えば、そこが次にGPU側へ寄せる場所です。

## 11. 結論

### 1スライド1メッセージ

PCNの5万ジョブ学習では、GPUOnly型に寄せる方針が実測でも文献でも支持される。

### 結論

- PCNでは環境rolloutが超線形に重く、CPU側は64コアで天井(11本/分)
- NNだけGPUに載せる分業型では、CPU側の環境実行と司会構造が律速のまま
- Nsightの実測: PCIe転送は0.5%で無罪。重いのは細かい発行(680枚/ステップ)と毎ステップの同期(CPUの83%が待機)、そしてオブジェクト⇄配列の変換
- 手書きカーネルで司会を排除し、rollout生成125.4本/分(64コアの11倍)・NN込みループも発行1.15倍まで圧縮。**いずれも全件一致の厳密性つき**
- 文献の位置づけ: 「分岐だらけ・状態が大きい環境はGPU苦手」という論文たち自身の警告のど真ん中で、スレッド割当とアルゴリズム移植で成立させた

## 12. 最後に言うこと

- GPUOnly化は「GPUが速いから」ではない
- PCNで遅かったのは「CPUが毎ステップ司会する構造」と「オブジェクトを1個ずつ触る形」
- それをGPU内でまとめて進める形に変えたのが今回の高速化の本質
- 部品(rollout生成)は50倍、全体は1.3〜1.4倍。残る律速(NN更新・リプレイ)を順にGPU側へ寄せていく

## 付録: 想定Q&A(質疑対策)

**Q1. 2枚で125.4本/分は1枚(93.5)の1.34倍にしかなっていないが?**
→ 2枚条件は1枚あたりの本数を半分(512×2)にした測定で、総本数は1枚B=1024と同じ。スケーリング効率の測定ではない。B増がほぼ無料(64→1024で374→657秒)なので、枚数・B両方にまだ伸び代がある。

**Q2. GPUを使い切っているのか?**
→ いいえ。1スレッド=1エピソード+tpb=1はワープの1/32しか使わない贅沢な使い方で、床はガラ空き。それでも司会排除と本数の横並びで50倍出る、というのが主張。使い切りは今後の伸び代。

**Q3. 「前は転送がボトルネックと言っていなかったか?」**
→ 正確にはPCIeの転送量(DMA)は0.5%で無罪。壁だったのはPythonオブジェクトを配列に詰め替える「変換」(75秒/8本)。転送の「場所」でなく「形」が壁、に言い直した。

**Q4. 分岐だらけの環境はGPUが苦手では? 論文もそう言っているが?**
→ その通りで、CuLE/Jumanjiも同じ告白をしている。うちはtpb=1でワープ発散を構造的に回避し、CPUの賢い逐次アルゴリズム(sweep-line・増分・早期打ち切り)をそのまま移植することで成立させた。tpb=32で32分/チャンクに劣化した実測が発散の証拠。

**Q5. 64コア11本/分の根拠は?**
→ 48並列の実測からの換算。1コア0.25本/分×64の理論値16に対し11なので並列効率69%(メモリ帯域の共有による)。

**Q6. 近似で速くしていないか?**
→ していない。(開始時刻・待ち時間・費用)50000/50000全件一致+バッファ溢れゼロ。7月に「速いが待ち時間を無視した」カーネルを作って捨てた経験から、今回は検証器を先に作った。

**Q7. で、学習は何倍速くなったの?**
→ 全体で1.3〜1.4倍(5時間→3.5〜4時間、v6実証中)。rolloutの50倍が全体に効かないのはNN更新・リプレイが残るため(アムダール則)。そこが次の対象。

**Q8. なぜXLA(JAX)のまま改善しなかった? CUDA Graphは?**
→ 試した。しかも**実際に効いていて、v4ではタイムラインの72.8%がCUDA Graph実行(77,446スパン、1周9個)になっている**。それでも速度は3%しか改善しなかった=**律速は発行削減では消えない**: 状態の持ち回りコピー(2MB×338回/周、graphの外で個別発行)、毎周3回のホスト同期+4バイトの継続確認、細切れカーネルの依存連鎖が残るため。だから構造ごと(手書きカーネルに)変えた。

## 付録B: Nsightタイムライン読み上げ台本(08-24 sqlite直接集計・確定値)

2枚のスクショを順に見せながらこの台本で話す。数字は全て下記の再現コマンドで出せる。

### B-1. 分業型(pcn_gpu_cpu.nsys-rep、計測区間2.22秒、128ジョブ)

1. **この画面は2.22秒間で、配置判断2,560回ぶん**。青いバー1群=1判断のNN推論(行列積gemv・clamp・argmaxなど微小カーネル25個、1個平均1.8μs)。
2. **GPUが計算していたのは合計112ms=画面の5.0%**。1判断0.87msのうちGPUの仕事は44μsだけ。
3. **バーの間の空白=CPUの時間**。環境(配置探索)の実行と、次のカーネル発行。発行(cudaLaunchKernel 64,000回)だけで289ms=GPU実計算(112ms)の**2.6倍**。「発行の方が計算より高い」状態。
4. 赤/緑の点=PCIe転送。H2D 3回/判断(平均489ns)+D2H 1回/判断(989ns)、**合計6.3ms=0.28%。転送は無罪の実証**。
5. 一言でいうと**交互演奏**: GPUとCPUが交代でしか働けず、どちらかが常に待つ。

### B-2. XLA工場 v4(j50k_scan_b64v4.nsys-rep、while区間275.6秒、5万ジョブ×B=64)

1. **仕事は全部GPU上に移した**(グレーの帯=1個のwhileループが275.6秒占有)。タイムラインの内訳: **CUDA Graph実行の封筒(オレンジ)72.8% / 個別カーネル(青)12.0% / D2Dコピー9.4% / 空白5.8%**。graph封筒の中身はこの記録粒度では不可視——「94%忙しそうに見えるが、スループットは手書きカーネルの1/37」が正確な言い方。
2. 青の正体: `loop_select_fusion_*` 等、XLAがループ本体から生成した細切れカーネル**292万個、1個平均11μs**。
3. オレンジの正体: 状態(carry)の持ち回りコピー**290万回、ほぼ全部2MB/回、総量5.8TB**。コピー中の帯域は225GB/s出ている=帯域は健全、**量と回数が異常**。busy時間で見るとカーネル33秒に対しコピー26秒=働いた時間の44%が計算でなく引っ越し。
4. **司会の動かぬ証拠**: たった**4バイトのD2H読み戻しが25,764回**=「ループを続けるか」の判定値を毎回CPUが確認。その結果、CPUスレッドは**cuStreamSynchronizeで229秒=区間の83%をブロック**(約16msごとに1回同期)。
5. 伝票: cuLaunchKernel 292万枚+コピー発行292万枚、1枚4.5μs。**1配置判断(約32ms)あたり約680枚**。
6. 一言でいうと**司会付き工場**: 工場は建ったのに、事務所(CPU)が伝票1枚ずつと2MBの台車で回している。

- docs旧値「実働18%・1ステップ21ms・D2D平均7KB」はsqlite全窓集計で**12.0%・約32ms・平均2MB**に訂正(18%は分母を180秒窓とした計算。分母をwhile区間275.6秒に統一)。680枚/ステップ・290万回・カーネル33秒/コピー26秒は一致を確認。
- 【08-24朝 GUI照合で追加訂正】タイムラインのオレンジ帯の正体は**GPU側のCUDA Graph実行の封筒**(77,446スパン=区間の72.8%、1周9個、平均2.59ms)で、当初の「CPU側」「79%は空白」という説明は誤りだった。graphスパン内の個別カーネルはこの記録粒度(graph単位トレース)では記録されないため、「実働12%」は**graph外の正味計算**を指す。GPUの空白そのものは約5.8%。

### B-6. 【08-24朝 開封実測】node粒度で封筒の中を見た(j50k_scan_b32_node.nsys-rep)
