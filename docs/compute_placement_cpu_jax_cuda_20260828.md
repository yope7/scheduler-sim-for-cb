### 数字の読み方(この文書の規約)

- **[実測]** ベンチ・本番ログの値 / **[算出]** コードの配列定義から計算した値 / **[推定]** 根拠つき見積り。
- **倍率より秒/本を優先して書く**。倍率は分母の条件差(B・e_max・k・trace・測定日)を隠すため。
- 分子と分母は同条件で測ったものだけで組む(過去にこれを破って誤った記録を残した)。

### P.1 何をしている研究なのか — クラウドバースティング

大学のスパコン(**オンプレミス** = 自前の計算機群)には、利用者からの計算依頼が次々に届く。
混んでいると依頼は順番待ちになる。ここで、あふれた分だけ**クラウド**(従量課金の外部計算資源)に
逃がすのが **クラウドバースティング(cloud bursting)** で、本研究の対象。

```
        利用者からのジョブ
             ↓
     ┌───────────────┐
     │  スケジューラ  │  ← 1個ごとに「どっちに置くか」を決める(これが研究対象)
     └───────────────┘
        ↙            ↘
  オンプレ(有限)      クラウド(実質無限だが金がかかる)
  待たされるが 無料    すぐ動くが 有料
```

**衝突する2つの都合**があるのがこの問題の本体。

- 全部オンプレに置く → **費用 0、でも待ち時間は最大**
- 全部クラウドに出す → **待ち時間は最小、でも費用は最大**

「どちらが正解」は決まらない。だから目標は**1つの答え**ではなく、
**良い妥協点の集合**(→ P.4 パレートフロント)を出せる仕組みを作ることになる。

### P.2 語彙 — ジョブ・ノード・イベント

| 語 | 意味 | この文書での記号 |
|---|---|---|
| **ジョブ** | 計算の依頼1件。**到着時刻・処理時間・必要ノード数**の3つで表す | `arrival` / `width` / `height` |
| **ノード** | 計算機1台。オンプレとクラウドで別々のプールを持つ | `n_on` / `n_cl` |
| **配置** | そのジョブを「**いつから・どのノードで**」動かすか決めること | `(start, nodes)` |
| **イベント(予約)** | 配置済みジョブの占有記録 `(start, end, 占有ノード集合)`。これを溜めた表が**イベント表** | `events` |
| **待ち時間** | `start − arrival`。到着してから動き出すまで | `wait` |
| **費用** | クラウドに出したときだけ `width × height`。オンプレは 0(すでに持っている設備だから) | `cost` |
| **窓** | 「この区間が空いているか」を判定する時間区間 `[t, t+width)` | — |
| **候補時刻** | 「ここなら空くかもしれない」と試す時刻。到着時刻と、既存イベントの終了時刻 | `cand` |
| **run** | **連続して並んだ空きノード**の並び | — |
| **断片** | 非連続配置のときの、飛び飛びになったノードの塊 | `frag`, 上限 `k` |
| **刈り取り(prune)** | もう二度と判定に関わらないイベントを表から落とすこと | — |

**ジョブは「時間 × ノード」の長方形**だと思うとよい。幅が処理時間 `width`、高さが必要ノード数 `height`。
スケジューリングとは、この長方形を盤面に**詰めていく**作業。

```
 node ↑
   7 │          CCCCCCCCCCCC          job C: height=2, width=12(クラウドへ)
   6 │          CCCCCCCCCCCC
   5 │
   4 │  AAAAAA           BBBBBBBB     job A: height=2, width=6
   3 │  AAAAAA           BBBBBBBB     job B: height=2, width=8
     └────────────────────────────────→ time
        ↑Aは到着してすぐ置けた
                  ↑Bはここまで待たされた(= wait。Bの到着時刻との差)

     幅 = 処理時間 width / 高さ = 必要ノード数 height
     この長方形を、重ならないように・できるだけ早い時刻に詰めるのがスケジューリング
```

**この研究のルール**(§0.2 の配置規則の背景):

1. **到着順に、先頭のジョブから1個ずつ決める**。いったん決めた配置は後から動かさない。
2. **オンプレのノードはバラバラでもよい**(非連続配置可)。どの台に置いても待ち時間は変わらないため。
3. **クラウドは連続した `height` 本が要る**(この研究のモデル上の制約)。
4. できるだけ**早い時刻**に置く。だから「候補時刻を早い順に試して、最初に入るところで決める」。

⚠️ ノード数(48,000 / 192,000 など)は実機の台数そのものではなく、
**ワークロードの規模に合わせて決めた容量の設定値**(`config.yml` の `n_on_premise_node` / `n_cloud_node`)。
どの実験系列でもクラウド側はオンプレ側の4倍に取ってある。

### P.3 1ステップ・1エピソードとは

| 語 | 意味 | 規模 |
|---|---|---|
| **1ステップ** | ジョブ1個について「置き場所を決めて、記録して、次の観測を作る」まで | ミリ秒のオーダー |
| **1エピソード(1本)** | ジョブ列を頭から最後まで1回さばききること | 5万ジョブ = **5万ステップ** |
| **ワークロード** | 使うジョブ列。実データ(**trace**)と人工データ(**合成**)がある | — |

実データは**大阪大学スパコンの FY2024 課金トレース**。課金1週間ぶんを切り出すと約5万ジョブになり、
これが本文書で「5万」と書いている単位(学習用の週を weekA、評価用の次の週を **weekB** と呼ぶ)。
分布は極端に偏っていて、**上位10ジョブだけで占有の約52%**を占める。

**「1エピソード = 5万ステップ」が本文書のコスト単位**。
以降の表に出てくる「秒/本」は、この5万ステップを1回まわすのに何秒かかるか。

### P.4 目的が2つある — パレートフロント

目的は **総費用**と**平均待ち時間**の2つで、どちらも小さいほどよい。両立しないので、
評価は「1点の良し悪し」ではなく**曲線の良し悪し**になる。

```
 平均待ち時間
     ↑
     │●  全オンプレ(費用0・待ち最大)
     │ ＼
     │   ＼ ● ● ●   ← ランダム方策(確率 p でクラウド)を p=0→1 で振った参照線
     │      ○ ○ ○     ← 賢い方策はこれより内側(同じ費用でより短い待ち)に行けるはず
     │           ＼
     │             ●  全クラウド(費用最大・待ち最小)
     └──────────────────────→ 総費用
```

- **パレートフロント(PF)**: 「片方を良くするにはもう片方を悪くするしかない」点だけを集めた集合。
- **参照線(p掃引)**: 各ジョブを確率 `p` でクラウドに出すだけのランダム方策。`p` を 0→1 に振ると
  上の曲線を描く。**これに勝てて初めて意味がある**、というベースライン。
  本文書に出てくる「`p=0.0` は全オンプレ = 最混雑」はこの掃引のこと。
- **HV(ハイパーボリューム)**: フロントの良さを1つの数字にした指標(囲む面積が広いほどよい)。

### P.5 なぜ強化学習なのか、「指令」とは何か

閾値ルール(「待ちが N 秒を超えたらクラウド」)でも点は作れるが、
**狙う点を変えるたびに作り直し**になる。そこで:

**PCN(Pareto Conditioned Networks)** = 「**この費用・この待ちを達成しろ**」という**指令**を
入力に足したニューラルネット方策。1つのネットのまま、指令を変えるだけでフロント上の
好きな点を狙える、という設計。

| 語 | 意味 |
|---|---|
| **観測(obs)** | 方策が見る入力ベクトル(**224次元**、内訳は §0.3)。**全ジョブ列は見えない** — キュー先頭5件と直近イベント30件だけ |
| **指令(command)** | `desired_return` = 目標の(待ち, 費用)、`horizon` = 残りステップ数。**実単位**(生の費用値・秒)であって 0〜1 の割合ではない(割合を渡して全指令が原点に潰れたバグがあった) |
| **行動(action)** | `0` = オンプレに置く / `1` = クラウドに出す / `2` = **後回し(defer)** |
| **後回し(defer)** | 今は置かず、そのジョブを行列の後ろへ回す。巨大ジョブが行列を塞ぐのを避けるための行動。1ジョブにつき回数上限あり |
| **rollout** | 方策を動かしてエピソードを1本作ること |
| **greedy / sample** | 行動の選び方。greedy は最大スコアを常に選ぶ(決定的) |
| **eval** | 指令を格子状に振って走らせ、フロントがどれだけ描けるかを測ること |

**学習の3段構え**(本文書の時間表に出てくる Phase1/2/3 はこれ):

```
Phase1  種まき   : ランダム(p掃引)やヒューリスティックでエピソードを大量に作る。   … 5万では192本
Phase2  真似する : Phase1 の軌跡を「その軌跡が実際に達成した値」を指令として教師あり学習
Phase3  回す     : ①指令を出して rollout ②良かったエピソードを保管庫に入れる
                   ③その保管庫でネットを更新   ——を1イテレーション(iter)として100回繰り返す
```

**分散実行の登場人物**(§2.4 の時間表に出てくる):

| 語 | 役割 |
|---|---|
| **Actor** | rollout を担当するワーカー。16本並列など。CPU または GPU |
| **Learner** | 集まったエピソードでネットを更新する係。GPU0 |
| **Ray** | Actor と Learner をつなぐ分散実行の枠組み。この転送自体が重い(§2.5) |
| **チャンク** | GPU で一度にまとめて走らせるエピソードの束。`chunk=64` なら64本同時 |

### P.6 だから「シミュレータの速さ」が研究の律速になる

1回の学習に必要なエピソード本数を数えると:

```
  Phase1 192本 + Phase3 16本 × 100 iter + eval(指令の格子) …… おおよそ 2,000 本弱
  × 1本 = 5万ステップ
```

**1本 240秒(改良前の CPU 1コア)なら、これだけで5日以上**かかる。
本文書の高速化は全部ここに効いていて、実際 9.2時間 → 4.3時間 になった(§4.4)。

そして**「速くしたら答えが変わった」は最悪**。学習結果を過去の run と比較できなくなるので、
高速化は**答えを1ビットも変えないこと**を検証してから入れる(§0.4)。
本文書に何度も出る「**ビット一致**」「**全件一致**」はこの規律のこと。

### P.7 3つの方式が「同じもの」を計算している、という意味

§2〜§4 で比べる3方式(CPU / JAX / CUDA)は、**同じジョブ列を同じ規則で配置するプログラム**であって、
アルゴリズムを変えたわけではない。違うのは**計算の並べ方**だけ。

```
   ジョブ列 ──▶ ┌─────────────────────────────────┐ ──▶ (費用, 待ち)
                │ 観測を作る → 方策が行動を選ぶ    │      = この1本の成績
                │      ↑              ↓           │
                │  イベント表 ◀── 配置探索(§0.2)  │
                └─────────────────────────────────┘
                        これを T=5万回まわす = 1エピソード
                        ↑ この箱の中身は3方式で同一。「誰がどう並べて回すか」だけが違う
```

- **方式A(CPU)**: 1本を1コアが縦に5万ステップ回す。
- **方式B(JAX/XLA)**: B 本を横に並べ、全レーンが同時に同じ命令を実行する。
- **方式C(CUDA)**: B 本を横に並べるが、ループごと GPU の中に入れて止まらないようにする。

だから3方式の出力 `(start_time, wait, cost)` は**完全に一致するはず**で、実際そう検証している。

### P.8 GPU 側の語彙(§4・§6 で使う分だけ)

| 語 | 意味 |
|---|---|
| **カーネル** | GPU に投げる仕事の単位。CPU が1枚ずつ「発行」する(発行1枚 ≈ 4.5μs) |
| **スレッド / ブロック / SM** | GPU の階層。スレッドが最小単位、それをまとめたのがブロック、ブロックが載る演算装置が SM(A40 は84個) |
| **ワープ** | 32スレッドの組。**同じ命令を一斉に**実行するので、組の中で分岐すると直列化する(= ワープ発散) |
| **tpb** | threads per block。1ブロックあたりのスレッド数 |
| **グローバルメモリ / 共有メモリ** | GPU のメインメモリ(遅い・大きい) / ブロック内だけで共有する高速メモリ(速い・小さい) |
| **atomic 演算** | 複数スレッドが同じ場所を同時に更新しても壊れないようにする加算など |
| **`syncthreads`** | ブロック内の全スレッドがそこに揃うまで待つ待ち合わせ |
| **numba** | Python の関数を CUDA カーネルにコンパイルするライブラリ。方式C はこれで書いている |
| **JAX / XLA** | 配列計算を書くと GPU 向けにコンパイルしてくれる枠組み。方式B はこれ |
| **`lax.scan` / pytree / SoA** | JAX でループを書く仕組み / 状態をまとめた入れ子構造 / 構造体の配列でなく配列の構造体で持つ形 |
| **ovf(オーバーフロー)** | 固定長で確保したバッファが足りなくなったこと。黙って壊れないようフラグで検知する |

### P.9 その他の用語(本文で初出のときに戻ってくる用)

|---|---|

| **argmax** | 「いちばん大きい要素の位置」を返す操作 |

**運用・実験まわり**

| 語 | 意味 |
|---|---|
| **正容量 / 過負荷容量** | そのワークロードが渋滞せずに流れるよう較正した容量 / それより小さく常時混雑する設定。過去の `n^2.6` は後者で測った値 |

| **warmup** | 本番計測の前の暖機(JAX では初回コンパイルを走らせること)。使わない経路の warmup が空転していた例が §3.5 |
| **格子評価** | 指令を等間隔に並べて全部走らせ、フロントを描く評価のやり方 |

**低レベルの語**

| 語 | 意味 |
|---|---|

| **CUDA Graph** | カーネルの発行列をまとめて1回で投げる仕組み(発行税の削減策) |
| **ゼロコピー** | 同じメモリをコピーせずに2つのライブラリで共有すること(§4.3 の numba ↔ torch) |
| **TorchScript / JIT trace** | PyTorch のモデルを追跡して最適化済みの形に固めること(`PCN_JIT_ACT`) |

## 0. 共通の計算内容 — 3方式が同じ答えを出すべき「1エピソード」

### 0.1 問題

ジョブ列 `T` 個を到着順に1個ずつ、**オンプレミス** か **クラウド** に割り当てる。

| 記号 | 意味 | 由来 |
|---|---|---|
| `arrival` | 到着時刻 | `jobs[j,0]` |
| `width` | 処理時間(占有する時間の長さ) | `jobs[j,1]` |
| `height` | 必要ノード数(占有するノードの本数) | `jobs[j,2]` |

- **オンプレ**: ノードは**バラバラでもよい**(非連続配置可)。費用 0。
- **クラウド**: **連続した** `height` 本が要る。費用 `width × height`。

目的は2つ(最小化): **総費用** と **平均待ち時間**
(`SCHEDULER_WAIT_METRIC=slowdown` のときは `wait / max(1, width)`)。

### 0.2 1ステップでやること(全方式の共通仕様)

参照実装は [`src/envs/scheduling_variants/event_native_env.py`](src/envs/scheduling_variants/event_native_env.py) の
`step` / `_find_event_allocation*` / `_pick_free_from_count` / `_record_event_schedule`。

```
1. 候補時刻の集合 = {arrival} ∪ {既存イベントの end のうち end >= arrival}
2. その集合を昇順に辿る。各候補 t について:
     窓 = [t, t+width)
     窓に重なる既存イベント(start_e < t+width かつ end_e > t)の占有ノードの和集合を取る
     count[node] = そのノードを占有している「窓内イベント」の数
     free = count==0 のノード
       - onprem: free の数 >= height なら成立
                 (最低位の連続 run を優先。無ければ free の昇順先頭 height 個 = 非連続)
       - cloud : 連続した height 本の run が必要。無ければ次候補へ
3. 最初に成立した t が start。wait = start - arrival。cost = width*height (cloud) / 0 (onprem)
4. イベント表に (start, start+width, 占有ノード) を追加
5. 観測ベクトル(224次元)を作って方策に渡す
```

**重要な性質**: 「どのノードを選ぶか」が以後の開始時刻に影響する。だから
「空きノードの**個数**だけ数えれば足りる」は厳密には成り立たない
(§3.4 の N軸消去はこの前提の上で成立条件を切っている。図6-c 参照)。

### 0.3 観測 224 次元の内訳

`event_c_env.py` の定数から:

| 部分 | 次元 | 中身 |
|---|---:|---|
| 直近イベント | `N_EVENTS_OBS(30) × EVENT_FEATURES(6)` = 180 | (start, end, width, use_cloud, start_node, height) を正規化 |
| ジョブキュー | `JOB_QUEUE_SIZE = 5 × 8` = 40 | 先頭5ジョブの生8列 |
| urgency | 1 | **現ジョブをオンプレに置いたときの開始時刻**(= 配置探索をもう1回) |
| efficiency | 3 | クラウドに置いたときの費用/利得/比(= 配置探索をさらにもう1回) |
| **合計** | **224** | |

**この観測が env コストの主因**。5万ステップ・単独・v9 フラグでの実測 [08-27]:
両方 ON = 69.1秒 / `SCHEDULER_OBS_EFFICIENCY=0` → 48.5秒 / `SCHEDULER_OBS_URGENCY=0` → 62.3秒 /
**両方 OFF → 27.2秒**。つまり **env コストの 61% は「観測を作るための追加の配置探索」**。
個別の差の和(20.6 + 6.8 = 27.4秒)より両方 OFF の差(41.9秒)が大きい = 足し算にならない
(キャッシュの効き方が絡む)。

urgency の探索結果は `_front_alloc_cache` で直後の本配置に再利用される(`PCN_REUSE_URGENCY_ALLOC`)。
**efficiency(クラウド側)は再利用されておらず、step 本体と重複している**(削れる余地)。

### 0.4 正確性の基準(3方式に共通のルール)

**すべての高速化は「答えを1ビットも変えない」ことを検証してから既定 ON にする**。
検証器は `scripts/proto_gpu_sweep/verify_*.py` に器具として残してある。

| 段 | 照合対象 | 実績 |

## 2. 方式A — CPU だけの Python 実装

### 2.1 データ構造

イベント表は **資源別の `list[dict]`**。ノード×時刻の盤面(ビットマップ)は**持たない**。
これが「イベント駆動」の意味で、メモリが `T × n_nodes` に爆発しない理由。

```python
self._resource_events = {False: [ ... ], True: [ ... ]}   # False=onprem, True=cloud

record = {
    "job_id": int, "start": int, "end": int, "width": int, "height": int,
    "use_cloud": bool, "start_node": int,
    "node_cols": None or [[node,...]] * width,   # 非連続配置のとき
    "nodes":    [node, ...],                      # 占有ノード
    "nodes_np": np.ndarray(intp),                 # 占有カウント更新用(生成時に1回だけ確保)
}
```

### 2.2 配置探索の5世代

| 世代 | フラグ | やったこと | 効果 |
|---|---|---|---|
| A0 | (なし) | 候補時刻ループ × 全イベント走査。実質 `O(R²)` | 基準 |
| A1 | `PCN_FAST_ENV` | ① **刈り取り**: `end < suffix_min_arrival[j]` のイベントは未来の窓に二度と重ならないので表から落とす ② occupied を作る同じ走査で `min_overlap_end` も取る(2回目の走査を消す) ③ 連続 run が見つかった瞬間 return | 指数そのものが下がる |
| A2 | `PCN_FAST_ENV_SWEEP` | **sweep-line**(時刻を早い順に1回舐めて占有を差分更新する。P.9): 候補を昇順に辿り、`order_start`/`order_end` の2順序配列を単調前進させて `count[node]` を**増分維持**。`O(R log R + R·H)` | 128ジョブ 3.7倍 → 1024ジョブ **8.2倍**(倍率が規模とともに上がる) |
| A3 | `PCN_FAST_ENV_NP` | `count` を `np.int32` にし、ENTER/EXIT を fancy-index の加減算に。pick は `diff`+`flatnonzero` でベクトル化 | さらに 2.7倍(pure Python 比 5.3倍) |
| A4 | `PCN_SWEEP_C` | sweep 本体を C 拡張 `event_sweep_alloc` に。Python は CSR を組むだけ | numpy 比 **4〜5倍**、pure Python 比 **26〜36倍** |
| A5 | `PCN_EVENT_CSR_CACHE` | C に渡す CSR を**追記で持ち回る**(毎回組み直さない) | ベンチ 単独 2.55倍 / 16並列 4.05倍、**本番 3.48倍** |

イベントが少ないうちは sweep より素朴な候補ループのほうが速いので `PCN_SWEEP_MIN_EVENTS=48` で切り替える
(どちらでも結果は同一)。

### 2.3 A5(CSR 持ち回り)— 「計算より、計算に渡す形を作るほうが重かった」

C 拡張 `event_sweep_alloc` は **CSR 形式**(可変長リストの束を「値を1本につないだ配列 + 各行の開始位置」で表す形。P.9)の4配列を要求する。

```
starts[n]      i64   イベントの開始時刻
ends[n]        i64   イベントの終了時刻
node_off[n+1]  i32   各イベントの占有ノードが nodes_flat のどこから始まるか
nodes_flat[m]  i32   占有ノードを全イベント分つないだ配列
```

イベント表が `list[dict]` なので、従来は**呼ぶたびに** `np.fromiter` 4回 + `np.concatenate` で
組み直していた。**5万ステップ・v9 フラグ・単独プロセスでのプロファイル実測**:

| 項目 | 値 |
|---|---|
| 探索の呼び出し回数 | **124,972 回**(= 2.50 回/step。本配置1 + urgency + efficiency) |
| 1回あたりの平均イベント数 R | **463** |
| 1ステップ **1.356 ms** の内訳 | 詰め直し **0.832 ms (61.4%)** / C本体 0.298 ms (22.0%) / その他 0.211 ms (15.5%) / 刈り取り 0.015 ms |

**実際の計算(0.298ms)より、その計算に渡す形を作るほう(0.832ms)が 2.8倍重かった**。
5万ステップで 41.6秒がここに消えていた。

対策は `_EventCSR`(容量を倍々に伸ばす追記バッファ)を持ち回るだけ。イベント表を書き換える場所は
**reset / 追加 / 刈り取り の3か所しかない**のでフックはそこだけ。表自体は `list[dict]` のまま残した
(表を読む経路が配置探索3種・記録・観測構築と多く、置換は影響範囲が広すぎるため)。
行数が食い違ったら自動で組み直す安全弁つき。変更は `event_native_env.py` のみ・約120行。

⚠️ **この節の 1.356 ms/step(= 5万換算 67.8秒)と §2.4 の「改修前 59.3秒」と §0.3 の「69.1秒」は
別条件の測定**(プロファイル計装あり / 素の壁時計 / env.step 単体ループ)。同じ列に並べないこと。

### 2.6 CPU 方式に残っている無駄と限界

- **C 拡張の中に per-call のやり直しが残っている**。`event_sweep_alloc` は**呼び出しごとに**
  `malloc` 4本 + `calloc` 2本 + **`qsort` 2回**(`order_start`/`order_end` を毎回ゼロから作り直す)。
  CSR 持ち回りで消したのは Python 側の詰め直しだけで、**C 本体 0.298ms の中に `O(R log R)` のソートが
  124,972回分残っている**。イベント表の変化は毎回「1件挿入 + 刈り取り」なので、
  order 配列も持ち回れるはず = 次の一手。
- **C 拡張は GIL(Python の大域ロック。P.9)を解放していない**(`Py_BEGIN_ALLOW_THREADS` がゼロ)。1プロセス内のスレッド並列には
  先に GIL 解放改修が要る。いまはプロセス(Ray Actor)並列のみ。
- **コアを増やしても効かない**。16並列で既に劣化 1.22倍、32並列で頭打ち、48並列で悪化。
  効くのは「1ステップの仕事量を減らすこと」だけ。
- 学習が進むほど rollout が重くなる(安い解 = オンプレ寄りを出すため混雑する)。
  終盤の1本が **68〜96分**に肥大する「ガチャ」があった。

## 3. 方式B — JAX / XLA によるバッチ実装(「工場」)

### 3.1 プログラミング様式(CPU からの書き換え規則)

JAX(XLA)は **コンパイル時に全部の形が決まっていないといけない**。ここが CPU 実装との最大の差。

| CPU で書けるもの | JAX での書き方 | 代償 |
|---|---|---|
| `list.append` で伸びる表 | **固定長 E_max にパディング**(足りない分を無効値で埋めて長さを揃える)。無効イベントは `start=INF64(2^62)`, `end=-1` | E_max を超えると溢れ(フラグで検知) |
| `while candidates:` の早期打ち切り | **全候補 T=E_max+1 を評価して `argmax`** | 仕事量が「最悪ケース固定」になる |
| `if use_cloud: ... else: ...` | `jnp.where` / `lax.select`(両方計算して選ぶ) | 両方の計算コストを払う |
| `for j in range(T)` | `lax.scan`(状態を pytree で持ち回る) | ループ制御が**ホスト側**に残る |
| `set` でユニーク化 | しない(同じ t を二度試しても最初の成立 t は不変なのでソートだけ) | — |
| dict のイベント表 | **SoA の `NamedTuple` pytree** | — |

無効候補は `BIG = 2^60` でパディングするとソート後尾に集まり、`valid_cand` マスクで除外できる
(`BIG + width` が `INF64` 未満に収まる関係を維持する)。

### 3.2 第1世代: dense カーネル(`gpu_sweep_jax` / `batch_env_jax`。**現在は退役**)

状態(`EnvState`)はこの形。**`occ` にノード軸を持つ**のが特徴で、これが後にメモリの主犯になる。

```
jobs_w (B,N) i64  jobs_h (B,N) i32  jobs_arr (B,N) i64  jobs_full (B,N,8) f64
idx (B,) i32      time (B,) i64     done (B,) bool
ev_start (B,2,E) i64   ev_end (B,2,E) i64   ev_len (B,2) i32
occ_on (B,E,n_on) bool   occ_cl (B,E,n_cl) bool     ← ノード軸。メモリの主犯
```

配置探索の作り方:

```python
# 1) 窓との重なり: overlap(B,T,E)
t_end = cand + width[:, None]
ov = (starts[:,None,:] < t_end[:,:,None]) & (ends[:,None,:] > cand[:,:,None])

# 2) 占有カウント: overlap(B,T,E) × occ(B,E,n) の fp16 行列積 → count(B,T,n)
cnt  = jnp.einsum("bte,ben->btn", ov.astype(f16), occ.astype(f16),
                  preferred_element_type=f32)
free = (cnt == 0.0)

# 3) 連続 run: free の累積和 cs について cs[n+h]-cs[n]==0 が「n から h 連続空き」
#    argmax で最低位開始(C 版と同じタイブレーク)
# 4) 最初に成立した候補 = feasible(B,T) の時刻昇順 argmax
```

**設計上の要点**

- **`scatter` は致命的に遅い**。カウント更新を散布で書くと全域で einsum 版に負ける。
  「重なり行列 × 占有行列」に潰して **tensor core の行列積**に落とすのが正解だった。
- **fp16 で正確性が壊れない根拠**: 使うのは `cnt == 0` の bool だけで、
  **非負値の和が 0 になるのは全項が 0 のときだけ**。丸めは判定に影響しない
  (`v1h` は蓄積も fp16 にして `count` の書き出し帯域を半減させる。結果は v1 と完全一致)。
- **C 版とのタイブレーク一致**: 候補は昇順 / run は node 0 から最低位 / 非連続 pick は free の
  昇順先頭 height 個 / フォールバック start = `max(arrival, max(ends))`。
  ここを1つでも外すと「速いが違う答え」になる。

**メモリ**(この形状 `E=8192, T=8193, n_on=48000`)[算出]:

| テンソル | 要素数 | 1本あたり |
|---|---|---:|
| `occ (E, n_on)` bool | E·n | **393 MB** |
| `overlap (T, E)` bool | T·E | 67 MB |
| `count (T, n_on)` fp16 | T·n | **786 MB** |
| 計 | | **約1.25 GB**(この形状の場合) |

実運用形状での見積りは **1本あたり約350MB** [推定。判定表84MB + 途中結果の数倍] で、
**同時に載るのは 64〜96本が限界**だった。正しい容量(22,700/90,800)× 4096ジョブでは
**B=8 で 18.9 GiB** を要求して OOM した。**これが第2世代(§3.5)を作った直接の理由**。

### 3.3 4つの高速化(合成5万ジョブ・1エピソード) [実測 07-08]

### 3.4 第2世代: イベント駆動の厳密カーネル(`factory_defer_ev`。**現在の既定**)

dense マスクをやめ、**占有ノードを「区間 RLE」**(イベントごとの `[lo,hi)` 区間リスト)で持つ。
**ノード軸が状態から完全に消える**。

```
class EvState(NamedTuple):
  # ジョブ軸 (N = ジョブ数。ノード数ではない)
  jobs_w (B,N) i64 / jobs_h (B,N) i32 / jobs_arr (B,N) i64 / jobs_full (B,N,8) f64
  waits  (B,N) i64 / ev_obs (B,N,6) f64        ← 追加順イベント6特徴(圧縮しない)
  # 進行
  idx (B,) i32 / time (B,) i64 / done (B,) bool / cost_total (B,) i64 / mksp (B,) i64
  # onprem イベント(占有は区間プールへの参照)
  es_on/ee_on (B,Eo) i64 / eh_on (B,Eo) i32 / el_on (B,) i32
  iv_lo/iv_hi/iv_ev (B,P) i32 / pl (B,) i32     ← 区間 RLE のプール
  # cloud イベント(常に連続 [cl_lo, cl_lo+eh_cl))
  es_cl/ee_cl (B,Ec) i64 / eh_cl/cl_lo (B,Ec) i32 / el_cl (B,) i32
```

**3層構造**(全候補×全ノードのテンソルを作らないための計算削減):

```
[1] 全候補の安価な確実判定 (O(T log E)、ノード軸なし):
      free_lb = n - Σ h_e(窓に重なるイベントの高さ合計)  → free_lb >= h なら確実に成立
      free_ub = n - 窓内の最大時点被覆                    → free_ub <  h なら確実に不成立
      (時間重複するイベントはノードが互いに素、という配置規則の不変量を使う。
       窓内 max は es グリッド上の sparse table range-max で O(1)/候補)
[2] 上下界の間に落ちた「曖昧候補」だけを厳密評価(先頭 n_amb 個)
      区間端点をノード座標でソート → 被覆カウントの cumsum → 和集合 / 最長 run
[3] 選ばれた候補で1回だけノード pick(連続 run 最低位 or 昇順 greedy 充填)、断片は隣接マージ
```

**メモリ**(`T=50,000`, `Eo=Ec=2,560`, `P=5,120`)[算出]:

| 軸 | 内訳 | 1本あたり |
|---|---|---:|
| **ジョブ軸(支配項)** | `jobs_full 64B + ev_obs 48B + jobs_w 8 + jobs_arr 8 + waits 8 + jobs_h 4` = **140 B/ジョブ** | **7.00 MB** |
| イベント軸 | `es/ee/eh × 2資源` + `iv_lo/hi/ev` + `cl_lo` | 約 0.17 MB |
| **合計** | | **≈ 7.2 MB / 本** |

**dense の約1/70**。ノード数を増やしてもメモリは増えない(ジョブ数にだけ比例する)。
4096ジョブ × 正容量が **完全一致**で回る。

**溢れは全部フラグで検知**(`ovf_ev` / `ovf_pool` / `ovf_frag` / `ovf_amb`)。サイレント破綻なし。
既定は `e_alloc=2048`(または `min(N+1, 2560)`)/ `pool=2*e_on` / `n_amb=512` / `k_pick=16` / `kcompact=64`。
発火したらバッファを拡大して自動再実行する。副産物として dense カーネルの **int16 バグ**
(ノード数 ≥ 32768 で `free_cnt` が折り返す)も発見・修正した。

切り替えは `PCN_GPU_COUNT_KERNEL=ev`(既定) / `=count`(旧近似へ退避)。

### 3.5 本番形状での実行時間と、なぜ止まるのか

合成5万で 0.151秒/エピソードが出ても、**本番(厳密・実 trace・全機能)では 24秒/エピソード**。
しかも **B=64 でも 96 でも 24秒/ep で不変** = バッチを増やしても1本あたりが縮まない。

Nsight Systems での解剖(scan 定常部 **180秒窓**):

| 項目 | 値 |
|---|---|
| GPU がカーネルを実行していた時間 | 33秒 = **18%** |
| GPU 上のメモリコピー(D2D) | 26秒 = 14%(**290万回**、平均7KB の細切れ) |
| GPU が何もしていない時間 | **約67%** |
| `cuLaunchKernel` | **290万回**、1枚あたり平均 **4.5μs** |
| `nvidia-smi dmon` の表示 | sm=100%, mem=92% ← **稼働ランプであって出来高ではない** |

⚠️ 上の「290万回」は**この180秒窓の値**(180秒 / 21ms ≈ 8,571 step × 338 ≈ 2.9e6)。
5万ステップ全体の発行数ではない。

**1ステップ(21ms)の内訳**:

| 内訳 | 時間 | 1発あたり |
|---|---:|---:|
| GPU での計算(カーネル約340個) | ~3.8 ms | 約11 μs |
| GPU 上のコピー(338回) | ~3.0 ms | 約9 μs |
| 発行・同期・すきま(`cuStreamSynchronize` が全体の76%) | **~14 ms** | 発行1枚 4.5 μs |

**律速は「伝票発行」**。1ステップあたり **約680枚**(カーネル340 + コピー338)を CPU から発行し、
周回のたびに「続けるか」の判定値を CPU に読み戻す(D2H 3回/周)。
**XLA のループは司会が CPU 側にいる**のが構造的な原因で、CUDA Graph 化のフラグでは 3% しか直らなかった。

その他のコスト: **XLA のコンパイル約2分**(5万ジョブ形状・初回)、
生カーネル利用時にも使われない XLA 経路の **warmup 空回し 718〜724秒**。

**Phase3 の生産手段としての実測**: 旧 XLA 工場 = 約26分/iter(5万・1イテレーション分)。

### 3.6 それでも JAX 工場を残している理由

**機能等価性がいちばん厚い**のがこの経路だから。2026-08 の監査で以下まで等価化した(f64 で Δ 約 1e-16)。

- defer(3行動): 達成は完全一致、行動は 99.945% 一致
- `PCN_FC_DEPTH` 任意 / attn(MHA 2層)/ FiLM / Fourier 全種 / `PCN_COMMAND_BALANCE` /
  `PCN_COND_ADD_SCALE` / `PCN_COST_HOLD` / 占有観測 / `SCHEDULER_WAIT_METRIC=slowdown` /
  `PCN_MIX_REGIMES` / `PCN_MIX_JOBS` / `PCN_S_EMB_DROPOUT` など13項目以上
- **レジーム混合を黙って無視していた**のが条件付け崩壊の真因だった
  → 教訓: **ゲートは網羅的に書く。「無視される」が最悪**。

## 4. 方式C — CUDA(numba)の手書きカーネル

### 4.1 C-1: 1スレッド = 1エピソード(CuLE 方式)

**発想**: XLA の司会(ホスト同期)を排すには、**5万ステップのループごとカーネルの中に入れる**しかない。
1スレッドが1エピソードを丸ごと担当すれば、ループはカーネル内の `for j in range(T)` になり、
**発行は1回**で済む。行動列は事前生成して渡す(状態に依存しないので完全等価)。

**データ構造**(全てグローバルメモリ、エピソード別領域):

```
per-episode (資源別に完全分離: ev_on_* / ev_cl_*)
  ev_start[E_MAX] i64,  ev_end[E_MAX] i64,  ev_nfrag[E_MAX] i32
  ev_frag_lo[E_MAX][K] i32, ev_frag_hi[E_MAX][K] i32   … 占有ノード区間 [lo,hi)  ★メモリ支配項
  order_end[E_MAX] i32, order_start[E_MAX] i32          … 昇順の index 列(二分挿入で維持)
  counted[E_MAX] i8                                      … 二重計上の防止
  count_on[n_on] i32, count_cl[n_cl] i32                 … per-node の窓内占有イベント数
  出力: start_times[T] i64, waits[T] i64, costs[T] i64, ovf_flag i32
共有(read-only): jobs[T][8] f64, actions[B][T] i8, suffix_min[T] f64
```

**アルゴリズムの写し方**

- **候補列**: `order_end` を二分探索して `arrival` 以降を線形に辿る。
  CPU 版の `{arrival} ∪ {end>=arrival}` と同じ列を、集合を作らずに得る。
- **増分 sweep**: `order_start`/`order_end` を候補間で単調前進(CPU の `sweep` と同一構造)。
  1ジョブを終えるとき、ENTER が訪れた範囲の `counted` を減算して `count` を全ゼロへ戻す
  (**クエリごとに1回だけ O(E)**。毎回ゼロ埋めしない)。
- **pick**: `_pick_free_from_count` と同一規則。連続 run 昇順最初 → 無ければ onprem は free 先頭
  height 個(断片化、断片数 > K で `ovf=2`)、cloud は失敗して次候補へ。
- **prune**: `suffix_min_arrival` による刈り取りを CPU と同条件で実装。
- **早期打ち切りが本命の利点**: 成立した候補で即 return できる = **CPU の賢さを GPU の本数で掛け算する**。
  これが XLA 版(全候補評価)との決定的な差(図6-b)。

**性能の罠(3つとも実装で踏んだ)**

| 罠 | 症状 | 対策 | 効果 |
|---|---|---|---|
| 毎候補で占有を数え直す | 遅い | 増分維持に | **13倍** |
| `cuda.local.array(K)` を pick の断片リストに使う | K=128 でローカルメモリ溢れ → レジスタ退避 | グローバルのスクラッチ `(B,K)` へ移動 | **10倍** |
| `tpb=32` で呼ぶ | 32人1組(ワープ)に別々のエピソードを詰めると分岐のたびに直列化 | **`tpb=1` 固定**(1ブロック1スレッド=発散なし) | **4.9倍**(本番 Phase1 kernel 1923→390秒) |

**性能** [実測 08-21。5万ジョブ]:

| 構成 | 生産力 |
|---|---:|
| CPU 1コア | 0.25 本/分 |
| 既存 GPU 工場(XLA) | 2.5 本/分 |
| CPU 64コア | 11 本/分 |
| **手書きカーネル A40 1枚 (B=1024)** | **93.5 本/分** = 0.64 秒/本 |
| **手書きカーネル A40 2枚 (512×2)** | **125.4 本/分** |

`B=64 → 1024`(16倍)で所要は 374 → 657秒しか伸びない = **バッチはほぼ無料**(床が軽いため)。

**それでも 1本あたりは遅かった**: 5万・B=4 で **344.92秒 = 6.898 ms/step = 86.2 秒/本**。
CPU env の 0.465 ms/step の **14.8倍遅い**。1スレッドが5万ステップを順番に進めるので、
グローバルメモリのレイテンシ(400〜800サイクル ≈ 240ns)を他の仕事で埋められない。
しかも **A40 の 10,752 コアのうち B=64 なら 64個 = 0.6% しか使っていない**。

### 4.2 C-2: 1ブロック = 1エピソード(ブロック協調版)★ 現在の主力

**発想**: 1本をブロック(128スレッド)で手分けすれば、メモリ待ちが他スレッドの実行で埋まる。

**誰が何をするか**

| 仕事 | C-1(1スレッド) | C-2(128スレッド) |
|---|---|---|
| `count` のゼロ化 | 1スレッドが `n_on` 回 | **128人で分割** |
| ENTER / EXIT / RESET(占有カウント更新) | 逐次 | **128人で分割**(`atomic.add` + shared で集約) |
| pick(空きノードの探索) | 逐次 | **128人で区間分担** |
| 刈り取りの前詰め | 逐次 | 逐次(スレッド0) |
| イベント表への二分挿入 | 逐次 | 逐次(スレッド0) |
| 観測ベクトルの組み立て(lockstep 時) | 逐次 | 逐次(スレッド0) |

**pick の手分け方**(ここが効いた本体。図6-h):

```
各スレッドが自分の担当区間を1回だけ走査して、4つの値を出す:
   ① 先頭から続く空きの長さ  ② 末尾に続く空きの長さ
   ③ 区間内で完結する最初の連続 run   ④ 区間が全部空きか
→ スレッド0が区間を順に繋いで「最初に height 個続く位置」を決める
   (区間をまたぐ run は carry で持ち回るので、逐次版と同じ位置が選ばれる)
```

**ENTER/EXIT の範囲**は `order_start`/`order_end` が昇順なので **二分探索で確定**できる
(逐次に前進させるのと同じ範囲になる)。

**ビット一致の根拠**(並列化しても答えが変わらないと言い切れる理由):

1. `count` の最終値は **加算の総和** → 誰がどの順で足しても同じ。
2. `free_cnt` の増減は **「`atomic.add` の戻り値が 0 だった回数」の総和**。
   同じノードに複数イベントが入っても「戻り値 0」を観測するのは厳密に1回だけ → 順序に依らない。
3. pick / prune / 挿入は逐次のままなので元コードと同一。

**唯一の挙動差**: C-1 は連続 run を見つける前に断片が K 本を超えると `ovf=2` で打ち切るが、
C-2 は run を先に判定するので打ち切らない(run があるなら断片リストは使われないので結果は正しい)。
K=128 の実運用で断片がそこまで出た実績はなく、検証でも `ovf=0` で一致した。

**罠**: `if tid == 0:` の中に早期 `return` を書くと、残りのスレッドが `syncthreads` で待ち続けて
**デッドロック**する(終端観測 `j >= T` の return で踏んだ)。**抜けるときはブロック全員で抜ける**。

**性能** [実測 08-27。5万ジョブ・**B=4**・実 trace weekB・`e_max=8192, k=128`]:

| 構成 | 総時間 | ms/step | 秒/本 | 対 C-1 |
|---|---:|---:|---:|---:|
| C-1(1スレッドが1本を担当) | 344.92秒 | 6.898 | 86.2 | 1.0 |
| C-2(1ブロック=1本、**pick は1スレッド**) | 67.7秒 | 1.355 | 16.9 | 5.1× |
| **C-2(1ブロック=1本、pick も128人で手分け)** | **16.9秒** | **0.337** | **4.2** | **20.5×** |
| 参考: CPU env(CSR 修正後・単独) | 23.2秒 | 0.465 | 23.2 | — |

**tpb の効き**(pick が1スレッドのとき、B=4): 64→75.5秒 / 128→**67.7秒** / 256→67.3秒。
**128 で頭打ち = 残っているのは手分けしていない pick**、という判定ができた。
👉 **「スレッドを増やしても速くならない」は、次に手分けすべき場所を指している**。

**本数と効率** [B ごとの実測。同じ 5万・weekB]:

| 構成 | 秒/本 |
|---|---:|
| CPU 16並列(CSR 修正後) | 1.78 |
| GPU C-2 B=4 | 4.2(本数が少なすぎて損) |
| GPU C-2 B=64 | **0.38** |
| GPU C-2 B=256 | **0.26** |

**1波の壁時計**(同じ本数を作り終えるまで。CPU は16並列):

| 本数 | CPU | GPU | 倍率 |
|---:|---:|---:|---:|
| 16 | 28.4秒 | 約18秒[推定] | 1.6× |
| 64 | 114秒 | 24.1秒 | 4.7× |
| 256 | 454秒 | 66.4秒 | **6.8×** |

👉 **損益分岐は B ≈ 24〜32**。過去に2回「GPU は16本では勝てない」と主張したが、
それは **1スレッド1本という実装を所与にした誤り**だった。

**メモリ** [算出。`e_max=8192, k=128, n_on=48000, n_cl=192000, T=50000`。
**k は `gpu_factory` 既定・検証器の値**であって、関数シグネチャの既定 16 ではない]:

| 領域 | 1エピソードあたり | 内訳 |

**支配項は `k`(断片上限)**。ノード数でもジョブ数でもない。
B=256 で **2.85 GB**、B=1024 で **11.4 GB**。A40(48GB)の床はまだ空いているが、
**溢れ時の自動拡大は `e_max → max(2e, 65536)` / `k → k×4`** なので、
`k=512` に上がると frag だけで 33.5 MB/本(合計 36.3 MB/本)= B=256 で 9.3 GB になる。
fast100 本番では ovf の再実行ログは出ておらず、`e_max=8192 / k=128` のまま走っている。

### 4.3 C-3: lockstep(NN 方策を挟む GPU 完結 rollout)

**問題**: C-1/C-2 は「行動列を事前に渡す」前提。NN 方策は行動が状態依存なので、
カーネルの中から torch を呼ぶことはできない。

**解**: ループをホストに出し、**1ステップだけ全エピソードを進める**カーネルにする。

```
for j in range(T):                                  ← ホスト側の Python ループ
    obs_kernel[B, 128](j)     # 全 B 本の観測 obs[:, j, :224] を GPU 構築
    logits = model(obs, desired_return, horizon)    # torch バッチ推論(B本まとめて)
    action = argmax(logits)                         # greedy
    step_kernel[B, 128](j, action)                  # j 番目のジョブを配置
    desired_return = f32(f64(desired_return) - reward)   # 指令更新(B本ベクトル化)
    desired_horizon = clamp(desired_horizon - 1, min=1)
```

**1周 = 発行「段」が5つ**(obs / NN / argmax / step / 指令更新)。ただし
**実際の CUDA launch は torch の内訳を含めて数十発**(過去の計測で NN 推論だけで 33カーネル)。
XLA の 680枚に対して1桁小さい、という話であって「5枚」ではない。
**発行税は実測 1.15倍**(step 分割のみで 430〜488秒 vs ベース 375〜407秒)。

**ゼロコピー接続**: obs/actions/waits/costs は **torch cuda tensor** として確保し、
`numba.cuda.as_cuda_array()`(`__cuda_array_interface__` 経由)で numba カーネルに渡す。
**同一ポインタ**を確認済み。numba カーネル(legacy default stream)と torch の current stream
(同じく legacy default stream)は**同一ストリームで直列化される**ので、
ループ内にホスト同期は一切不要(全 step 非同期発行 → 最後に `synchronize` 1回)。

**観測カーネルの増分化**(ここで一度つまずいた):

| 構成(5万・B=64) | 時間 | 対ベース |
|---|---:|---:|
| ベース(全周1カーネル・観測なし) | 375〜407秒 | 1.0 |
| step 分割のみ | 430〜488秒 | 1.15〜1.2(発行税ほぼゼロ) |
| step + 観測(素朴 = 毎周全走査) | 1,695秒 | **4.16** |
| step + 観測(増分化後) | 659秒 | **1.76** |

増分化の工夫: 観測が要る「直近30イベント」の候補を **生死問わず**上位 `cand_m` 件で持ち回る
(**生存だけ持つ prune は不可** — 時刻が非単調に動くので死んだイベントが蘇生し得る)。
さらに urgency/efficiency のプローブが解いた配置クエリを直後の本配置で**再利用**する
(CPU 版 `PCN_REUSE_URGENCY_ALLOC` の GPU 版)。

**`cand_m` の掃引**(5万・実 trace weekB・B=2・ブロック版):

| cand_m | 64 | 256 | 1024 | **2048** | 4096 |
|---|---:|---:|---:|---:|---:|
| ms/step | 3.308 | 1.801 | 1.321 | **1.082** | 1.216 |

小さいと生存30件が埋まらず「過去イベント全走査 `O(j)`(j は最大5万)」に落ちる。
大きすぎると挿入コストが勝つ。**2048 が底**なので既定にした(容量は正確性に無関係=全件一致)。
1スレッド版にも効く(502.8 → 398.9秒)。

**ブロック化の効果**: lockstep も 1スレッド → 1ブロック に組み替えて
**10.057 → 1.082 ms/step(9.3倍)**。手分け後に内訳を測ると **観測の組み立てが74%** に化けたが、
真因は `cand_m=64` が小さすぎたことだった(上の掃引で解決)。

**検証の階段**(全段で既存経路と厳密一致):

| 段 | 照合対象 | 結果 |
|---|---|---|
| B-1 配置(step 分割) | 既存 raw カーネル(5万×B=2) | **300,000/300,000 ビット一致** |
| B-2 観測(GPU 構築) | リプレイ経路(5万×B=1) | **11,200,000 セル完全一致** |
| B-3 NN 行動(greedy) | CPU `_run_episode`(実 ckpt・実指令×2) | **50,000/50,000 一致 ×2本、目的値の差 0.00** |
| B-4 統合スモーク | 学習2周(Phase1+Phase3 とも GPU 産) | 完走・エピソード流入確認 |

**Phase3 の生産手段としての比較**(5万・1イテレーション分):

| 手段 | 時間 |
|---|---:|
| CPU 16並列(序盤の軽い時期) | 約4分 |
| CPU 16並列(終盤・オンプレ寄り解の時期) | **68〜96分(ガチャ)** |

正直な評価: **序盤はまだ CPU が速い**。lockstep の価値は「速さ」より
**「分散の圧縮」(96分ガチャ → 定額)と「CPU コアの解放」**。

**メモリ**: C-2 の状態に加えて **`obs (B, T, 224)`**。

| 経路 | dtype | 1本あたり | B=64 |
|---|---|---:|---:|

👉 **観測の記録がメモリの主犯**(C-2 本体 11.1MB の4倍)。B を上げるときは `e_max` より先に obs が効く。

### 4.4 本番に載せたときの実効値(ベンチとは違う)

⚠️ **ベンチの倍率をそのまま成果値として掲げない**。報告には本番値を使う。

**v10 fast100(08-27夜)の実測。倍率は「秒/本」ベースで並べる**:

| 項目 | v9(夜) | fast100(夜) | 実効倍率 |
|---|---:|---:|---:|
| Phase1 カーネル(3chunk 平均) | 479.8秒 | 244.1秒 | **1.96×**(ベンチは20.9×) |
| Phase1 replay(CPU 側、CSR 修正の副産物) | 396.0秒 | 102.3秒 | 3.87× |
| rollout 待機 / iter | 163.8秒 | 74.0秒 | 2.21× |
| Learner 待ち / iter | 99.0秒 | 36.0秒 | 2.75× |
| **eval 1回** | **377.9秒** | **377.6秒** | **1.00×(手つかず)** |
| **学習全体** | **33,128秒** | **15,449秒** | **2.14×** |

**「2.20倍」と書かないこと**。マシンは共用で昼夜に約2.5%の差があり、
2.20 は `main100(昼) 33,960 / fast100(夜) 15,449` の値。**統制された比較は v9(夜) との 2.14倍**。
さらに fast100 と main100 は待ち時間フラグが2つ違う(`PCN_CMD_TRACK_WAIT_WEIGHT` / `PCN_CMD_WAIT_ZERO`)ので、
速度比較としても交絡している。

**ベンチ 20.9× が本番 1.96× になる理由(記録済み)**: ベンチは grid が小さい条件で、
**本番は `chunk_b=64` で旧カーネル(C-1)も既に GPU を埋めている**。
C-1 の 本番 479.8/64 = 7.5 秒/本 は 08-21 ベンチの B=64(374/64 = 5.8 秒/本)と概ね一致する。

**★ ただし本当に未解明な差が残っている**: 同じ B=64 で、
**ベンチ C-2 = 0.38 秒/本 に対し 本番 C-2 = 244.1/64 = 3.8 秒/本 = 10倍の乖離**。
これは倍率ではなく絶対値の差なので、負荷や条件差だけでは説明しにくい。候補仮説は2つ。

1. **ジョブ列の重さ**: 本番 Phase1 は `p ∈ {0.0,…,1.0}` の掃引で、`p=0.0` は全オンプレ=最混雑。
   ベンチは `p_list = [0.5]*B`。
2. **SM 占有率**: B=64 は 84 SM に 1ブロックずつしか載らず、SM あたり 128/1536 = 8.3%。
   レイテンシ隠蔽の材料が同一 SM 内に無い(図6-g)。

⚠️ ただし過去に同型の「cheap 端仮説」を**もっともらしいストーリーへの飛びつき=誤診**として記録している。
`verify_raw_rollout_block.py` を `B=64` かつ `p` 掃引で1回回して切り分けてから結論を書くこと。

### 5.2 「何が遅さを作るか」の変遷

```
2026-06  env の配置探索が O(R²)          → sweep-line + C 化で指数を下げる
2026-07  update が CPU のカーネル発行律速 → 一括化(1400発行/更新、GPU は暇だった)
2026-07  JAX 工場が「発行680枚/step」律速 → 司会ごと GPU に入れる決断(= 方式C)
2026-08  raw カーネルが「1スレッド1本」  → ブロック協調で 20.5倍(ベンチ)
2026-08  env が「C に渡す配列の詰め直し」 → CSR 持ち回りで 3.48倍(本番)
2026-08  ★ いまの律速は3つ:
           ① NN forward(rollout の 53〜55%)
           ② Learner の直列(36〜99秒/iter)
           ③ eval が丸ごと手つかず(377.6秒 × 5 = fast100 の壁時計の 12.2%)
```

**一般則**: GPU 高速化の失敗パターンの第1位は「計算が遅い」ではなく **「仕事を細かく渡しすぎ」**。
本プロジェクトではこの「発行律速」が **3回** 再発した(推論の 33カーネル/推論、
学習 update の CPU 発行律速、env scan の 680発行/step)。

### 5.3 スケーリング則

- CPU env の実行時間は概ね **仕事量 ΣR(生存イベント数)× 単価**。
- 刈り取りが無かった当時は `R ∝ n/2` で **n^2.58**。C 化と刈り取りで **指数そのものが 1.74 まで下がった**
  (「指数は変わらない」は反証済み)。
- **正しい容量なら合成は n^1.03**。実 trace は長いジョブで R が刈れず **n^1.75**
  = 実データの大規模化に GPU 一括生成が要った理由。
- 過去の「n^2.6・1.7年」は **当時の実装と過負荷容量の産物**であって、問題の本質ではなかった。
- 安い端の評価は本物の **O(N²)**(指数1.99を実測)。厳密な O(N log N) は不可能
  (ノードの同一性に依存するため)。件数ベースの区間 sweep で平均待ちの誤差 0.3〜3%(コストは完全一致)。

### (I) スケジューリングの動き — 「何を計算しているか」の図

#### 図6-a. node × time 平面での1回の配置(いちばん基本の1枚)

```
 node
  ↑
 7│              ┌─────┐
 6│    ┌───┐     │  E3 │
 5│    │E1 │     │     │
 4│    │   │     └─────┘
 3│    └───┘        ┌──────┐
 2│         ┌────┐  │  E4  │
 1│         │ E2 │  └──────┘
 0│         └────┘
  └──────────────────────────────→ time
        ↑arrival    ├─ 窓 [t, t+width) ─┤

  窓に重なるイベント = start_e < t+width かつ end_e > t     … E3, E4
  count[node] += 1 (ENTER) / -= 1 (EXIT)                    … C の 1348-1360 行がそのまま絵になる
  free = count==0 のノード
  → onprem: free の数 >= height なら成立(最低位の連続 run 優先)
  → cloud : 連続した height 本の run が必要
```

**添える数字**: 1回の探索で見る平均イベント数 **R = 463**、
1ステップあたりの探索回数 **2.50 回**(本配置 + urgency + efficiency)。

#### 図6-b. 候補時刻の昇順スキャンと早期打ち切り(方式B と C を分ける理由)

```
候補時刻: t1 = arrival,  t2, t3, ... (既存イベントの end のうち end >= arrival を昇順)

  t1 ──▶ 台帳照合(窓に重なる予約の席数を増分カウント) ──▶ 満席 ✗
  t2 ──▶ 差分だけ更新                                 ──▶ 満席 ✗
  t3 ──▶ 差分だけ更新                                 ──▶ 空きあり ✓  ← ここで打ち切り
  t4, t5, ... は見ない

  方式A(CPU)  : 打ち切れる
  方式C(CUDA) : 打ち切れる   ← CPU の賢さ × GPU の本数
  方式B(XLA)  : 打ち切れない ← 全候補 T=E_max+1 を評価して argmax。仕事量が最悪ケース固定
```

**これが「1本は遅いのに全体は速い / 全体も遅い」を分ける本体**。図1(方式の並べ方)と対にして出す。

#### 図6-c. オンプレ(非連続)と クラウド(連続矩形)— N軸消去が厳密には成り立たない理由

```
 オンプレ: height=3 のジョブを、空きが飛び飛びでも置ける
   node 0 1 2 3 4 5 6 7
        ■ □ ■ □ □ ■ □ □      ■=占有  □=空き
          ↑   ↑ ↑             → 昇順先頭3個 {1,3,4} に置ける(非連続)

 クラウド: 連続した 3 本が要る
   node 0 1 2 3 4 5 6 7
        ■ □ ■ □ □ ■ □ □
                          → {3,4} は2本しかない / {6,7} も2本 → 不成立、次候補へ

 ★「空き数だけ数える」近似が壊れる場面:
   時間的に重ならない2つのイベント A,B は同じノードを共有し得る。
   窓が A と B の両方を跨ぐと、「高さの合計」は 2 つ分だが「占有ノードの和集合」は 1 つ分かもしれない。
   → 件数ベース近似は過密帯で待ちが 34〜100% ずれた(だから ev カーネルの区間 RLE に移った)
```

#### 図6-d. イベント表の成長と刈り取り(なぜ T に比例しないか)

```
イベント数
   ↑
   │        ╱╲    ╱╲╱╲        ← 刈り取り(prune)で頭打ちになる
   │   ╱╲╱╲  ╲╱╲╱      ╲╱╲╱   平均 R = 463
   │  ╱                        ← 刈り取りが無ければ R ∝ n/2 で増え続ける(旧: n^2.58)
   └──────────────────────────→ ジョブ番号 j (0 .. 50,000)

  刈り取りの条件: end < suffix_min_arrival[j]
     = 「残りのジョブの最小到着時刻」より前に終わるイベントは、未来の窓に二度と重ならない
  発火閾値: len(events) >= prune_at、実行後 prune_at = max(64, 2*残数+32)  ← 償却的

```

```
    B=64 → 64 ブロック × 1 スレッド = 64 スレッド
    SM:  ████████████████████████████░░░░░░░░░░░░  64/84 SM に 1本ずつ
    SM内占有率: 1/1536 = 0.07%  ← レイテンシを隠す相手がいない

(b) C-2: 1ブロック = 1エピソード、tpb=128
    B=64 → 64 ブロック × 128 スレッド = 8,192 スレッド
    SM:  ████████████████████████████░░░░░░░░░░░░  64/84 SM = 76.2% に 1ブロックずつ
    SM内占有率: 128/1536 = 8.3%   ← ブロック内でなら隠せるが、SM はまだガラ空き

    👉 B を 84 の倍数に増やすと SM あたりの常駐ブロックが増えて更に隠れる
       (B=256 で 0.26 秒/本 まで下がるのはこれで説明がつく)
```

**「10,752コアのうち 8,192 が動いている」とは書かない**。動いているのは 8,192 **スレッド**で、
SM の常駐余裕は 8.3% しか使っていない。この区別が §4.4 の「本番で 10倍遅い」の第一候補にもなる。

#### 図6-h. 1ステップの中で「誰が何をするか」(手分けの境界線)

```
        C-1(1スレッド)                    C-2(128スレッド)
  ┌────────────────────────┐      ┌────────────────────────────────┐
  │ count のゼロ化          │      │ ×128 で分割                    │  手分け
  │ ENTER / EXIT / RESET    │      │ ×128 で atomic.add + shared集約 │  手分け
  │ pick(空きノード探索)    │      │ ×128 で区間分担 → carry で結合  │  手分け ← ここで4.0倍
  ├────────────────────────┤      ├────────────────────────────────┤
  │ 刈り取り(前詰め)        │      │ スレッド0が逐次                 │  逐次のまま
  │ イベント表への二分挿入  │      │ スレッド0が逐次                 │  逐次のまま
  │ 観測ベクトルの組み立て  │      │ スレッド0が逐次                 │  逐次のまま
  └────────────────────────┘      └────────────────────────────────┘

pick の区間分担:
     thread0        thread1         thread2        ...
  ├───────────┤├───────────┤├───────────┤   ノード列を128等分
  各スレッドが1回だけ走査して4つの値を出す:
     ① 先頭から続く空きの長さ  ② 末尾に続く空きの長さ
     ③ 区間内で完結する最初の run     ④ 区間が全部空きか
  スレッド0が左から繋ぐ: carry(前の区間の末尾空き) + ① >= height なら区間跨ぎの run が成立
  → 逐次版と同じ「最低位の位置」が選ばれる(= ビット一致)
```

## 8. 教訓(索引)

詳細は各節にあるので、ここは見出しだけ。

### 計測

1. **分子と分母の測定条件が違う割り算をしない** → §2.4 の rollout 内訳
2. **「工程」と「その中の処理」を混同しない** → §2.4、図6-l
3. **ベンチの倍率を成果値として掲げない** → §4.4(20.9× → 1.96×)、§2.4(4.05× → 3.48×)
4. **倍率でなく秒/本で並べる**。倍率は分母の条件差を隠す → §5.1、§4.4 の10倍差の発見
5. **共用マシンの昼夜差(2.5%)を統制する** → §4.4(2.20 ではなく 2.14)
6. **稼働率はプロファイラのタイムラインで示す**(dmon の 100% は稼働ランプ) → §3.5
7. **規模が変わったら内訳を測り直す**(1024ジョブの「NN 69%」は5万で逆転) → §2.4
8. **切り分けの差は足し算にならない** → §0.3、図6-m

### 設計

9. **倍率を規模とともに上げたければ、最高次の項そのものを下げる** → §2.2、§5.3
10. **「スレッドを増やしても速くならない」は次に手分けすべき場所を指している** → §4.2
11. **実際の計算より、その計算に渡す形を作るほうが重いことがある** → §2.3
12. **並列にすると効く最適化と、しない最適化がある** → §2.4
13. **足し算の総和と atomic の戻り値だけで作れば、順序が変わっても答えは変わらない** → §4.2
14. **ゲートは網羅的に書く。「無視される」が最悪** → §3.6
15. **速度と正しさのトレードに飛びつく前に、症状の真因を切り分ける** → §3.3(N軸消去)
16. **学習は工場(近似でよい)・評価は厳密 env** → 工場の greedy 評価は argmax が僅差で振れて PF が退化する

### 実装

17. `cuda.local.array(K)` は K が大きいとローカルメモリ溢れで **10倍遅くなる** → §4.1
18. **`if tid == 0:` の中の早期 return はデッドロック** → §4.2
19. **ワープ発散**: 32人1組に別々のエピソードを詰めると直列化(tpb=32 は tpb=1 の5倍遅い) → §4.1
20. **XLA の `scatter` は致命的に遅い**。行列積に潰せるなら潰す → §3.2
21. **バッファ容量は正確性に無関係でも速度に効く**(`cand_m` 64 → 2048 で 3.3倍) → §4.3
22. **生存だけを持つ prune は観測バッファでは不可**(死んだイベントが蘇生し得る) → §4.3
