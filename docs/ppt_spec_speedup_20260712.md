## 1. 目的・読者・ゴール

- **目的**: 大学教授への進捗報告。「クラスタ・シミュレーションを GPU（JAX）で高速化した」ことを、なぜ・どこで・どれだけ、の順に理解してもらう。
- **読者**: 大学教授 1 名（対面プレゼン想定）。**HPC・ジョブスケジューリング・クラスタ運用は専門**。一方で **JAX・GPU 並列計算・「なぜ GPU だと速いか」・CPU/GPU の役割分担は、ほぼ予備知識なし** と想定する。したがって RL/JAX 用語は必ず §3 の定義に沿って平易に。HPC 用語（ジョブ・ノード・待ち時間）は説明不要。
- **持ち帰ってほしい 3 点（このプレゼンのゴール）**:
  1. なぜ高速化が必要だったか（大規模学習と大量評価が、超線形に重いシミュレーションを要求する）。
  2. 何をしたか（配置探索を GPU 上で数百エピソードまとめて回す「エピソード工場」）。
  3. どれだけ速いか、そして **どこに効いてどこに効かないか**（正直な位置づけ）。

## 3. 用語辞書（Glossary）★スライド 13「用語辞書」の中身 兼 表記統一の基準

**この列の「正規表記」を全スライドで厳守**する（言い換え・揺れを作らない）。「教授向け定義」はスライドやノートでの説明文。

| 正規表記 | 略記 | 教授向け定義（この言い回しに寄せる） |
|---|---|---|
| **パレートフロント** | PF | クラウド費用と平均待ち時間の、これ以上両立を良くできない境界の曲線（トレードオフ曲線）。 |
| **配置探索** | ― | 届いたジョブを「いつ・どのノードに置くか（またはクラウドに出すか）」を決める処理。シミュレーション計算の約 9 割を占める。 |
| **エピソード** | ― | 全ジョブ列を頭から最後までシミュレーションし切る 1 回分。 |
| **ロールアウト** | ― | 方策に従ってエピソードを実行し、経験（状態・行動・結果）を集めること。 |
| **エピソード工場** | 工場 | GPU 上でエピソードを数百本まとめて量産する仕組み。本研究の高速化の主役。「データ工場」とは書かず「エピソード工場」で統一。 |
| **オンプレ** | ― | 自前で持つ計算クラスタ。ノードは空いていればどこに置いてもよい（非連続配置可）。 |
| **クラウド** | ― | 足りない分を借りる外部計算資源（クラウドバースティング）。 |
| **弾性クラウド** | ― | 「クラウドは実質いくらでも即時に借りられる＝順番待ちが起きない」とみなす近似。 |
| **N 軸消去** | ― | オンプレの空きを「どのノードが空きか（ノード 1 台ずつ）」でなく「何台空きか（数だけ）」で持つ最適化。ノード列（N 軸）が消えるのでこの名。 |
| **JAX** | ― | NumPy とほぼ同じ書き方の数式を、そのまま GPU で高速実行できる数値計算ライブラリ（自動微分・JIT・vmap 付き）。 |
| **JIT（コンパイル）** | JIT | Python の関数を一度だけ GPU 用の機械語（カーネル）に変換し、以後は高速に走らせる仕組み。 |
| **vmap** | ― | 「1 本用に書いた処理」を、書き換えずに「N 本同時」へ自動拡張する変換（自動バッチ化）。 |
| **scan** | ― | 時間ステップの for ループを 1 つの GPU カーネルに融合し、毎ステップの CPU↔GPU 往復をなくす仕組み。 |
| **カーネル** | ― | GPU 上で走る 1 つの計算処理のかたまり。 |
| **GPU 常駐** | ― | データが GPU のメモリ上に置かれたままの状態（CPU との転送が発生しない）。 |
| **CPU** | ― | 逐次・分岐の多い処理が得意な汎用プロセッサ。 |
| **GPU** | ― | 同じ計算を大量に並列するのが桁違いに得意な演算装置。 |
| **Ray** | ― | CPU で複数のプロセス（アクター）を並列に動かす分散実行ライブラリ。本研究では 16 アクター＝16 コア並列。 |
| **方策** | ― | 状態を入力に「次の行動」を出すニューラルネット（AI 本体）。「ポリシー」とは書かず「方策」で統一。 |
| **指令** | ― | 方策に与える目標値（「この費用・この待ち時間を達成せよ」）。指令を変えて評価するとパレートフロント上の別の点が得られる。 |
| **PCN** | PCN | Pareto Conditioned Networks。指令で条件付けして 1 つの方策に多数のトレードオフ点を学ばせる多目的強化学習の手法。 |
| **バッチ** | B | 同時に並列処理するエピソード（や問題）の本数。B=256 なら 256 本同時。 |
| **秒/エピソード** | s/ep | 1 エピソードの実行にかかる実時間（壁時計）。 |

## 4. 表記ルール（ブレ防止・厳守）

1. **倍率は必ず `×73` 形式**（半角バツ `×` ＋ 数字）。「73倍」「x73」「73x」「73倍速」は使わない。図・見出し・本文すべて `×73`。
2. **時間は「2.81 秒」または「2.81 s/ep」**。同一スライド内では表記を混在させない。見出しは「秒」、表は「s/ep」を推奨。
3. **大きなジョブ数**: 見出し・口語は「**5 万ジョブ**」、表・正確値は「**50,000 ジョブ**」。中間表記（"5万件" "50k"）は使わない。
4. **英字略語は大文字**: JAX / GPU / CPU / NN / PCN / PF / Ray / JIT。文中でもこの綴り。
5. **カタカナ表記の固定**: パレートフロント / エピソード / カーネル / クラウド / オンプレ / バッチ / ロールアウト（長音・送りをこの通りに）。
6. **「方策」で統一**（「ポリシー」「エージェント」「AI」は口語ノートでのみ可、スライド本文は「方策」）。
7. **「エピソード工場」で統一**（「データ工場」「ファクトリ」不可）。
8. **比較基準を必ず明示**: 倍率を書くときは「対 CPU 1 コア」「対 16 コア CPU」「対 C（1 コア）」のどれかを併記する。基準なしの裸の倍率を書かない。
9. **日付**: 「2026-07-12」形式（ハイフン区切り）。
10. **小数**: 実測値は本書の桁数のまま（例 2.81、206.6、×11.8）。勝手に丸めない・増やさない。

## 5. スライド構成（1 枚ずつの指定）

各スライドは「タイトル / キーメッセージ（1 文）/ 本文要素 / 図・数字 / ノート」を満たす。順序厳守。

### S1. 表紙
- タイトル: **スケジューラ・シミュレーションの高速化 ── なぜ・どこで・どれだけ**
- サブ: クラウドバースティング向け強化学習スケジューラ / 2026-07-12
- ノート: 本日は「なぜ速くする必要があったか→何をしたか→どれだけ速いか、そして正直な限界」を話します。

### S2. 結論（3 行サマリ）
- キーメッセージ: 配置探索を GPU で数百本まとめて回し、大規模で大きく速くなった。
- 本文（3 点）:
  - 配置探索カーネル: **対 C（1 コア）×11.8**（GPU 常駐時）。
  - 5 万ジョブ 1 エピソード: **CPU 1 コア 206.6 秒 → GPU 1 枚 2.81 秒（×73）**。
  - ただし **効くのは大規模・大量評価のときだけ**（普通サイズの学習は速くならない）。
- ノート: 詳細はこのあと。まず全体像だけ。

### S3. なぜ高速化が必要だったか
- キーメッセージ: 目標（1 度の学習でどんな負荷でも最適 PF を引く）が、大量シミュレーションを要求する。
- 本文:
  - 研究の狙い: **1 つの方策を一度学習すれば、どんな負荷でも推論だけで最適パレートフロントを引く**。
  - そのため ①大規模（実クラスタ 1 週間＝数万ジョブ）で学習したい ②PF は多数の指令で 1 本ずつ評価して描く。
  - 壁: **シミュレーションがジョブ数に対して超線形（ほぼ二乗的）に重い** → 大規模学習も細かい評価も現実時間で回らない。
- 図: なし（または「ジョブ数↑で計算時間が二乗的に伸びる」概念曲線）。
- ノート: 超線形の理由は「置いたジョブが増えるほど、次の置き場所探しで見る対象も増える」から。

### S4. 計算のどこが重いか
- キーメッセージ: 重いのは配置探索（環境シミュレーション）で、全体の約 9 割。
- 本文（RL の 1 サイクル 3 要素）:
  - ①環境シミュレーション（クラスタ再現・配置探索）… **約 9 割**。
  - ②方策の推論（NN が置き方を出力）。
  - ③方策の更新（経験で NN を学習）。
- ノート: だから「①をいかに速くするか」が主戦場。

### S5. CPU と GPU の役割分担 ★図
- キーメッセージ: CPU は逐次・分岐が得意、GPU は同じ計算の大量並列が得意。①を GPU の土俵に乗せた。
- 本文（対比）:
  - CPU: 1 エピソードを分岐しながら 1 個ずつ。従来は 16 コアで 16 本並列（Ray）。弱点＝同時本数がコア数上限。
  - GPU: まったく同じ形の計算を数百〜数千まとめて一斉に。1 本・分岐だらけは不得意。
  - 施策: ①環境シミュレーションを「エピソードを束にして同じ手順で一斉に進める」形へ書き替え、②推論と合わせて GPU に載せた。
- 図: **役割分担図（新規作図・§7 図B）**。左 CPU ボックス／右 GPU ボックス／下に「16 本 → 数百本」。
- ノート: ここが速さの源泉。CPU が 16 本のところ GPU は 256〜1024 本。

### S6. やったこと＝エピソード工場
- キーメッセージ: 環境・推論・一部更新を GPU 上でまとめて量産する「エピソード工場」を作った。
- 本文:
  - エピソードを **バッチ B=256〜1024** で同時にロールアウト。
  - 配置探索・報酬・観測・行動を 1 つの GPU カーネルに融合（scan）。
- 図: 工場の概念図（多数のエピソードが GPU を通って経験データになる）。任意。
- ノート: CPU 版と結果が統計的に一致することを確認済み（正確性は担保）。

### S7. JAX とは何か
- キーメッセージ: JAX = NumPy の書き方のまま GPU で動かせる数値計算ライブラリ。3 つの機能が効いた。
- 本文（表 = §3 の JIT/vmap/scan）:
  - JIT: 関数を GPU 機械語に変換して高速化。
  - vmap: 1 本用の処理を自動で N 本同時に。
  - scan: 時間ループを 1 カーネルに融合し CPU↔GPU 往復をなくす。
- ノート: 教授の言葉で言えば「手で CUDA を書かずに、数式そのままで GPU 並列が得られる」。

### S8. なぜ JAX を選んだか（PyTorch でなく）
- キーメッセージ: 主役は「環境シミュレーションそのものの GPU 並列化」。関数変換に強い JAX が適していた。
- 本文:
  - NN 学習だけなら PyTorch でも十分。しかし今回は **配置探索（動的な制御フロー）を GPU カーネルに融合**したい。
  - JAX の scan/vmap（関数変換）がこれに本質的に向く。
  - 純関数なので **CPU 参照実装との数値一致（ビット一致）を検証しやすい** → 各段で結果不変を確認できた。
- ノート: 「速いだけでなく、正しさを確かめながら進められた」ことが選定理由。

### S9. どれだけ速くなったか（実測）★図
- キーメッセージ: 5 万ジョブは対 1 コア ×73。3 つの測定点で本物の数字。
- 本文（§6 の表を要約）:
  - 配置探索カーネル: 対 C（1 コア）**×11.8**（GPU 常駐時）。
  - エピソード工場（128 ジョブ）: 対 16 コア **×3.6**（対 1 コア ×57）。
  - エピソード工場（5 万ジョブ）: 対 1 コア **×73**（対 16 コア ×4.6）。
- 図: **`docs/figures/jax_speedup_20260712.png`（既存・§7 図A）をそのまま貼る**。
- ノート: 2026-07-12 に実機で測り直した値。

### S10. なぜ大規模ほど有利か
- キーメッセージ: CPU は超線形、GPU 工場はほぼ線形。だからジョブが多いほど差が開く。
- 本文:
  - CPU: 1 ステップが O(走っているジョブ数) → 超線形に重い。
  - GPU 工場: 同時に見るイベント数を固定枠（例 2,048）に抑え、ほぼ線形で頭打ち。
  - 結果: 128 ジョブでは僅差、5 万ジョブでは大差。
- 図: 概念線 2 本（超線形 vs 線形）。任意。
- ノート: N 軸消去（オンプレは空き台数だけ数える）がこの線形化の核。詳しくは別資料。

### S11. 正直な注記（公平性・C との関係）
- キーメッセージ: 比較は近い条件での実測。CPU も C 拡張で速く、Cが速くなるほど JAX の相対優位は縮む。
- 本文:
  - 比較は「同ジョブ数・同分布・同 C 版シミュレータ・観測込み」の近い条件。GPU/CPU で乱数経路が別なので厳密同一ジョブ列ではない。桁は堅い。
  - **C 拡張と JAX は競合する高速化**。CPU が速くなるほど GPU の相対優位は下がる（通常規模では CPU が以前比 約 3.7 倍速く、工場優位はかつて ×5〜15 → 今回 ×2〜3.6 に縮小）。
- ノート: 誇張しないための重要スライド。必ず入れる。

### S12. どこに効いて、どこに効かないか
- キーメッセージ: 普通サイズの学習は速くならない。効くのは大規模と大量評価だけ。
- 本文:
  - 通常（128〜512 ジョブ）: 律速は「データ作り」でなく「NN 更新」側 → 工場を速くしても総時間は変わらない。
  - 効く場面: ①超大規模（5 万ジョブ級）②オフラインで大量のエピソードを一気に生成（PF の多指令評価など）。
- ノート: 役割のはっきりした道具、という位置づけで締める。

### S13. 実験の現状と今後
- キーメッセージ: 各段は実装・検証済み。本体統合はゲートで用意、採用は大規模/大量評価に限定。
- 本文（状態表）:
  - 配置探索カーネル GPU 化（C 版と一致）: 済。
  - 環境シミュレーション全体のバッチ GPU 化（全ステップ一致）: 済。
  - 評価（指令格子）のバッチ GPU 化（行動列一致）: 済。
  - エピソード工場（分布一致）: 済。
  - 学習本体への統合（ゲート、既定 OFF）: 実装済・採用は大規模/大量評価に限定。
  - 今後: (a) 5 万ジョブ級の学習を 1 本通す土台 (b) PF 評価の大量生成。並行して汎化の本命＝スケールフリー環境設計。
- ノート: 「速くする」から「大きく 1 回学習して任意負荷で PF」へつなぐ。

### 6-1. 実測の代表値
| 測定対象 | 比較基準 | 速度 | 前提・注記 |

| 配置探索カーネル（単体） | C 実装 1 コア | **×11.8** | GPU 常駐時。単発呼び（CPU↔GPU 転送込み）だと **×1.5** に落ちる |

### 6-2. 5 万ジョブ 1 エピソードの生時間
- CPU 1 コア（C 版シミュレータ）: **206.6 秒/エピソード**
- GPU 1 枚（JAX 融合）: **2.81 秒/エピソード**
- → **×73**（対 1 コア）、**×4.6**（対 16 コア並列 = 206.6 ÷ 16 ≈ 12.9 秒 と比較）

### 6-3. GPU 内部の作り込み（別測定・2026-07-08）※出典を明記して使う
- 素朴な JAX 実装から最適化を積み上げ、5 万ジョブが **9.0 秒 → 0.151 秒（60 倍）**。
- 内訳（積み上げ）: 9.0 → 4.78（カーネル訂正 ×1.9）→ 2.21（弾性クラウド ×2.2）→ 0.31（**N 軸消去 ×7.1・最大**）→ 0.151（GPU 2 枚 ×1.9）。
- 対 16 コア CPU: 合成データで **22 倍**、実トレースデータで **5 倍**。
- ※ 6-2 の 2.81 秒（今回・1 GPU・素直な設定）と、この 0.151 秒（2026-07-08・2 GPU・全最適化）は**別条件の別測定**。混同しないこと。両方載せる場合は「今回の再実測 = 2.81 秒 / 作り込みの上限 = 0.151 秒」と役割を分けて書く。

### 6-4. 環境
- JAX 0.4.28、CUDA GPU 2 枚（各 46 GB 級）。計測は warm-up（コンパイル）後、`block_until_ready` で GPU 同期をとった実時間。
